웹에 데이터를 저장하는 5가지 방법

바이브코딩으로 앱을 만들다 보면 반드시 마주치는 질문이 있습니다. "사용자가 입력한 이 값을 어디에 두어야 하나?" 새로고침해도 남아야 하는지, 탭을 닫으면 사라져야 하는지, 서버도 알아야 하는지에 따라 답이 달라집니다. AI에게 "저장해줘"라고만 하면 대부분 localStorage를 쓰는데, 그게 항상 맞는 선택은 아닙니다.

  • 브라우저가 제공하는 저장 방식 5가지의 차이를 표 하나로 파악하기
  • 각 방식의 실제 동작하는 코드와 언제 쓰는지
  • "이럴 땐 이걸" — 3분 안에 고르는 의사결정 순서
  • 토큰 저장·용량 초과·데이터 소멸 등 실전에서 터지는 함정

먼저 알아둘 것: 여기서 다루는 것은 모두 브라우저(사용자 기기) 안에 저장하는 방법입니다. 사용자가 브라우저를 바꾸거나 다른 기기에서 접속하면 그 데이터는 없습니다. 여러 기기에서 같은 데이터를 봐야 한다면 반드시 서버 DB(Supabase, Firebase 등)가 필요합니다. 브라우저 저장소는 그 보조 수단입니다.

표를 가로로 밀어 보면 첫 열은 고정돼 따라옵니다. 초록은 유리한 쪽, 붉은색은 제약이 있는 쪽입니다. 어느 것도 전부 초록이 아니라는 점이 핵심입니다. 상황에 따라 고르는 것이지 우열이 있는 게 아닙니다.

용량 차이 — 숫자로는 실감이 안 나는 부분

용량 숫자는 "대략"입니다. 브라우저·기기·남은 디스크 공간에 따라 달라지고, 특히 IndexedDB는 고정값이 아니라 디스크 여유 공간에 비례해 배분됩니다. 5MB, 10MB 같은 수치를 코드에 못 박아 두지 말고 초과할 수 있다고 보고 예외 처리하는 편이 안전합니다.

수명 — 시간이 흐르면 무엇이 남는가

위 위젯의 단추를 순서대로 눌러 보세요. sessionStorage가 가장 먼저 사라지고, 쿠키가 만료일에 사라지고, 나머지는 사용자가 지울 때까지 남습니다. 이 한 장이 사실상 이 문서의 결론입니다.

2. Cookie — 서버가 같이 봐야 할 때

한 줄 브라우저가 매 HTTP 요청 헤더에 자동으로 실어 보내는 작은 문자열.

쓸 때 로그인 세션, 서버가 판단에 써야 하는 값(언어 설정, A/B 테스트 그룹).

피할 때 서버가 알 필요 없는 데이터. 매 요청에 딸려 가서 낭비입니다.

쿠키가 나머지 넷과 결정적으로 다른 점은 서버로 자동 전송된다는 것입니다. 이미지 하나를 불러올 때도 쿠키가 함께 갑니다. 그래서 크고 잦으면 그대로 성능 비용이 됩니다. 맨 위 구조도에서 브라우저 밖으로 나가는 화살표가 쿠키 하나뿐이었던 이유입니다.

// 저장 — 만료 7일, 전체 경로, HTTPS에서만, 크로스사이트 전송 제한
document.cookie = "theme=dark; max-age=" + 60*60*24*7 + "; path=/; secure; samesite=lax";

// 읽기 — 표준 조회 API가 없어 직접 파싱해야 합니다
function getCookie(name) {
  return document.cookie
    .split("; ")
    .find(row => row.startsWith(name + "="))
    ?.split("=")[1];
}
getCookie("theme");   // "dark"

// 삭제 — 만료를 과거로 보냅니다
document.cookie = "theme=; max-age=0; path=/";
장점
  • 서버와 클라이언트가 같은 값을 공유하는 유일한 방식
  • 만료 시각을 정밀하게 지정 가능
  • HttpOnly 옵션을 쓰면 JS가 못 읽어 XSS로부터 안전
  • 서브도메인 간 공유 가능 (domain 속성)
단점
  • 1개당 약 4KB — 거의 아무것도 못 담습니다
  • 매 요청에 실려 가 트래픽·지연 증가
  • 조회 API가 없어 문자열 한 덩어리를 직접 파싱
  • CSRF 공격의 통로가 됨 → SameSite 필수
  • 동의 배너 등 개인정보 규제 대상

중요: 로그인 토큰을 안전하게 두려면 HttpOnly 쿠키여야 하는데, 이 옵션은 서버가 Set-Cookie 헤더로 내려줄 때만 붙일 수 있습니다. 위 예제처럼 JS document.cookie로 만든 쿠키에는 붙지 않습니다. Supabase Auth 같은 라이브러리가 이 처리를 대신 해주는 이유입니다.

3. sessionStorage — 이 탭에서만, 지금만

한 줄 탭 하나에 묶인 임시 저장소. 탭을 닫으면 사라집니다.

쓸 때 작성 중인 폼 임시 저장, 여러 단계 입력 마법사, 스크롤 위치 복원.

피할 때 다음에 다시 방문했을 때도 남아 있어야 하는 값.

// 문자열만 저장됩니다. 객체는 JSON으로 변환합니다.
sessionStorage.setItem("step", "2");
sessionStorage.setItem("form", JSON.stringify({ name: "홍길동", email: "" }));

sessionStorage.getItem("step");                    // "2"  ← 문자열입니다
JSON.parse(sessionStorage.getItem("form")).name;   // "홍길동"

sessionStorage.removeItem("step");
sessionStorage.clear();     // 이 탭의 저장 내용 전체 삭제

범위가 탭 단위라는 점이 핵심입니다. 같은 사이트를 두 탭에 열면 각자 별개의 저장소를 씁니다. 새로고침(F5)은 살아남지만, 탭을 닫으면 없어집니다.

장점
  • API가 두 줄이면 끝날 만큼 단순
  • 탭마다 격리 — 여러 창에서 다른 작업을 동시에 가능
  • 뒷정리가 자동. 남은 쓰레기 데이터 걱정이 없음
  • 서버로 전송되지 않아 요청이 가벼움
단점
  • 탭을 닫으면 소멸 — 실수로 닫으면 그대로 날아감
  • 문자열만 — 매번 JSON.stringify/parse
  • 동기 API라 큰 데이터를 쓰면 화면이 멈춤
  • 약 5MB 제한

4. localStorage — 가장 흔하게 쓰는 기본값

한 줄 브라우저에 계속 남는 간단한 키-값 저장소.

쓸 때 테마(다크모드), 언어, "다시 보지 않기", 최근 검색어, 소규모 설정.

피할 때 로그인 토큰, 개인정보, 수 MB 이상의 데이터.

API는 sessionStorage와 완전히 같고 수명과 범위만 다릅니다. 탭을 닫아도, 브라우저를 껐다 켜도 남습니다. 같은 사이트의 모든 탭이 같은 저장소를 공유합니다.

localStorage.setItem("theme", "dark");
localStorage.getItem("theme");        // "dark"
localStorage.getItem("없는키");        // null  ← 빈 문자열이 아니라 null

// 다른 탭에서 값이 바뀌면 이 이벤트가 옵니다. 탭 간 동기화에 유용합니다.
window.addEventListener("storage", (e) => {
  if (e.key === "theme") applyTheme(e.newValue);
});

// 저장소가 막혀 있을 수 있어(사생활 보호 모드·용량 초과·차단 설정)
// 실무에서는 try/catch로 감쌉니다.
function save(key, value) {
  try {
    localStorage.setItem(key, JSON.stringify(value));
    return true;
  } catch (err) {
    console.warn("저장 실패:", err.name);   // QuotaExceededError 등
    return false;
  }
}
장점
  • 가장 배우기 쉽고 모든 브라우저가 지원
  • 브라우저를 껐다 켜도 유지
  • storage 이벤트로 탭 간 동기화가 공짜
  • 서버 없이도 "설정이 기억되는" 경험을 만들 수 있음
단점
  • JS가 그대로 읽음 — XSS 한 방에 전부 유출
  • 동기 API — 큰 값을 읽고 쓰는 동안 화면이 멈춤
  • 문자열만, 약 5~10MB
  • 검색·정렬 불가. 전부 읽어와 직접 걸러야 함
  • 사용자가 브라우저 정리로 언제든 지울 수 있음

가장 많이 하는 실수: 로그인 토큰(JWT)을 localStorage에 넣는 것. 페이지에 삽입된 악성 스크립트 한 줄이면 localStorage.getItem("token")으로 그대로 가져갑니다. 세션은 HttpOnly 쿠키에 두고, localStorage에는 유출돼도 곤란하지 않은 값만 담으세요.

동기 API가 화면을 멈춘다 — 직접 재보기
이 사각형은 계속 돌고 있습니다. 아래 단추를 누르면 어떻게 되는지 보세요.

아직 측정하지 않았습니다.

동기 저장이 도는 동안 사각형이 잠깐 멈춥니다. 그 시간 동안 브라우저는 클릭도 스크롤도 처리하지 못합니다. 비동기 쪽은 같은 양을 써도 애니메이션이 끊기지 않습니다. 스크롤할 때마다 localStorage에 쓰는 코드가 왜 버벅이는지가 여기서 보입니다.

5. IndexedDB — 많고 복잡한 데이터

한 줄 브라우저 안에 들어 있는 진짜 데이터베이스. 비동기·트랜잭션·인덱스를 갖췄습니다.

쓸 때 오프라인 노트/메모 앱, 이미지·파일 보관, 수천 건 이상의 목록, 대화 기록.

피할 때 값 몇 개만 저장하면 되는 경우. 배보다 배꼽이 큽니다.

객체를 객체 그대로 넣을 수 있습니다. 배열, 날짜, 심지어 이미지 파일(Blob)도 변환 없이 들어갑니다. 비동기라서 큰 데이터를 다뤄도 화면이 멈추지 않습니다. 대신 기본 API가 이벤트 콜백 기반이라 장황합니다.

기본 API (라이브러리 없이)

const req = indexedDB.open("notesDB", 1);

// 스키마는 여기서만 바꿀 수 있습니다 (버전이 올라갈 때 1회 실행)
req.onupgradeneeded = (e) => {
  const db = e.target.result;
  const store = db.createObjectStore("notes", { keyPath: "id", autoIncrement: true });
  store.createIndex("byDate", "createdAt");   // 날짜로 검색하려고 인덱스를 만듭니다
};

req.onsuccess = (e) => {
  const db = e.target.result;
  const tx = db.transaction("notes", "readwrite");
  tx.objectStore("notes").add({ title: "첫 메모", body: "…", createdAt: new Date() });
  tx.oncomplete = () => console.log("저장 완료");
};

실무에서는 래퍼를 씁니다

위 코드를 매번 쓰긴 번거로워, 보통 idb나 Dexie.js 같은 얇은 래퍼로 감쌉니다. Claude Code에게 "IndexedDB 써줘"라고 하면 대개 이쪽을 제안합니다.

import { openDB } from "idb";

const db = await openDB("notesDB", 1, {
  upgrade(db) {
    db.createObjectStore("notes", { keyPath: "id", autoIncrement: true });
  },
});

await db.add("notes", { title: "첫 메모", createdAt: new Date() });
const all = await db.getAll("notes");     // 객체 배열 그대로 돌아옵니다
장점
  • 용량이 사실상 넉넉함 (수백 MB~GB)
  • 객체·배열·파일·Blob을 변환 없이 저장
  • 비동기 — 대용량에도 화면이 멈추지 않음
  • 인덱스·범위 검색·트랜잭션 지원
  • Service Worker와 함께 완전한 오프라인 앱 구현 가능
단점
  • 기본 API가 장황하고 배우기 어려움
  • 스키마 변경(버전 업그레이드) 관리가 번거로움
  • 모든 조작이 비동기라 코드 흐름이 복잡해짐
  • 저장 공간이 부족하면 통째로 정리될 수 있음
  • 역시 JS가 읽으므로 XSS에 취약

6. Cache API — 파일·응답을 통째로

한 줄 HTTP 요청과 응답 쌍을 저장하는 전용 저장소. 주로 Service Worker와 함께 씁니다.

쓸 때 PWA 오프라인 지원, 이미지·CSS·JS 같은 정적 파일 캐싱.

피할 때 사용자가 입력한 값. 그건 위 네 가지 중에서 고릅니다.

// 앱 껍데기를 미리 받아 둡니다 (Service Worker의 install 단계)
const cache = await caches.open("app-v1");
await cache.addAll(["/", "/index.html", "/style.css", "/logo.png"]);

// 네트워크가 끊겼을 때 캐시에서 응답합니다
self.addEventListener("fetch", (e) => {
  e.respondWith(
    caches.match(e.request).then(hit => hit || fetch(e.request))
  );
});

나머지 넷과 성격이 다릅니다. 사용자 데이터가 아니라 "파일"을 저장하는 곳입니다. IndexedDB와 같은 저장 할당량을 나눠 씁니다.

7. 3분 안에 고르는 순서

위에서부터 읽어 내려가다가 처음 "그렇다"가 나오는 곳에서 멈추면 됩니다.

  1. 서버도 이 값을 알아야 하나? → Cookie. 특히 로그인 세션이라면 서버가 내려주는 HttpOnly 쿠키.
  2. 탭을 닫으면 사라져도 되나? 오히려 사라져야 하나? → sessionStorage. 작성 중인 폼, 다단계 입력의 현재 단계.
  3. HTTP 응답이나 파일을 통째로 두는 건가? → Cache API. 오프라인 대응, 정적 자원 캐싱.
  4. 데이터가 수 MB를 넘거나, 목록을 검색·정렬해야 하나? → IndexedDB. 오프라인 노트, 이미지 저장, 수천 건 목록.
  5. 그 밖의 작은 설정값 → localStorage. 여기까지 왔다면 이게 정답입니다.

저장한 뒤 새로고침해 보고, 이어서 이 페이지를 새 탭으로 열어 보세요. sessionStorage만 비어 있을 겁니다. 이 데모가 남기는 값은 "전부 지우기"로 정리됩니다.

① 브라우저 저장소는 "안전한 곳"이 아니다

개발자 도구 → Application 탭을 열면 localStorage, sessionStorage, IndexedDB의 내용이 전부 그대로 보이고 수정도 됩니다. API 키, 비밀번호, 결제 정보를 두면 안 되는 이유입니다. 값을 검증해야 한다면 반드시 서버에서 다시 확인해야 합니다. 클라이언트가 보내온 isAdmin: true를 그대로 믿으면 안 됩니다.

② 저장이 실패할 수 있다

사생활 보호 모드, 용량 초과, 사용자가 사이트 데이터를 차단한 경우 setItem이 예외를 던집니다. 저장 코드는 try/catch로 감싸고, 저장이 안 돼도 앱이 정상 동작하도록 만드세요. 바로 위 데모가 이 처리를 실제로 하고 있습니다. 이 파일을 file://로 열었다면 몇 가지는 빨간 글씨로 실패가 뜰 텐데, 그게 정상입니다.

③ 데이터는 언제든 사라질 수 있다

사용자의 브라우저 정리, 디스크 공간 부족으로 인한 자동 삭제, 브라우저의 추적 방지 정책(특히 Safari는 일정 기간 방문이 없으면 스크립트가 쓴 저장소를 정리합니다)에 의해 지워질 수 있습니다. "있으면 좋고 없어도 되는" 데이터만 브라우저에 두는 것이 원칙입니다. 꼭 남아야 한다면 서버로 보내세요.

④ 저장소는 출처(origin)마다 별개다

https://example.com과 https://app.example.com은 서로의 저장소를 볼 수 없습니다. http와 https도 다른 출처입니다. 로컬 개발 중 localhost:3000에 저장한 값이 배포 주소에서 안 보이는 것은 정상 동작입니다. 맨 위 구조도의 "출처 B" 상자가 이것을 나타냅니다.

⑤ 값은 항상 문자열로 돌아온다

localStorage.setItem("count", 5);
localStorage.getItem("count") + 1;          // "51"  ← 문자열 연결
Number(localStorage.getItem("count")) + 1;  // 6     ← 이렇게

localStorage.setItem("agreed", false);
if (localStorage.getItem("agreed")) { ... } // 항상 참! "false"라는 문자열이 들어 있으므로

⑥ 동기 API는 화면을 멈춘다

localStorage와 sessionStorage는 동기 방식이라, 큰 값을 읽고 쓰는 동안 화면 전체가 멈춥니다. 4절의 측정 위젯에서 직접 확인한 그대로입니다. 데이터가 커지거나 저장이 잦다면 IndexedDB로 옮기세요.

9. 정리

  • 기본값은 localStorage — 작은 설정값이라면 고민할 것 없이 이걸로 시작합니다.
  • 탭을 닫으면 사라져야 하면 sessionStorage — API는 똑같고 수명만 다릅니다.
  • 서버가 알아야 하면 Cookie — 로그인은 서버가 내려주는 HttpOnly 쿠키로.
  • 커지거나 검색이 필요하면 IndexedDB — 래퍼 라이브러리(idb, Dexie)를 함께 씁니다.
  • 파일·응답 캐싱은 Cache API — 오프라인 대응 전용입니다.
  • 비밀은 어디에도 두지 않습니다 — 브라우저 저장소는 사용자가 전부 볼 수 있습니다.

AI에게 요청할 때의 팁: "저장해줘"라고만 하면 대부분 localStorage가 나옵니다. 수명과 범위를 함께 말해주면 훨씬 정확한 코드가 나옵니다. 예를 들어 "이 폼 입력값을 탭을 닫으면 사라지게 임시 저장해줘", "이미지 목록을 오프라인에서도 보이게 저장해줘"처럼 조건을 붙이세요.
