01왜 이런 자동화가 필요한가

여러 언론사 사이트를 하루에도 몇 번씩 직접 돌아다니는 대신, 서버 없이 자동으로 모으고 정리하고 보내게 만듭니다.

이번 교안은 지금까지 따로 배운 조각들 — Claude Code로 프로젝트 만들기, Vercel 배포, GitHub CLI, Secrets 등록 — 를 하나로 엮어 실제로 매일 돌아가는 서비스를 만드는 종합 실습입니다. 결과물은 세 가지입니다.

  • 2시간마다 분야별 RSS 피드에서 새 기사를 자동 수집
  • 웹 페이지로 분야별 정리 + 급상승 키워드 하이라이트
  • 하루 1회 Claude가 분야별로 요약한 브리핑을 Discord 채널에 자동 전송
이 실습에서 새로 배우는 것

지금까지는 "만들고 한 번 배포"까지였다면, 이번엔 서버 없이 정기적으로 실행되는 자동화(GitHub Actions 스케줄)와 레포지토리 자체를 데이터 저장소로 쓰는 방식, 그리고 Webhook으로 외부 서비스(Discord)에 결과를 밀어넣는 법을 다룹니다.

02전체 구조 한눈에 보기

서버도, 별도 데이터베이스도 없습니다. GitHub Actions 두 개 + 리포지토리에 커밋하는 JSON 파일 + Vercel의 Git 연동이 전부입니다.

왜 별도 데이터베이스를 안 쓰나요?

수집 주기(2시간)와 트래픽 규모를 생각하면, 리포지토리에 JSON을 직접 커밋하는 것으로 충분합니다. Vercel은 Git 연동이 되어 있으면 push를 감지해서 알아서 재배포하므로, "데이터가 바뀌면 화면도 갱신된다"는 흐름을 DB 없이 그대로 얻을 수 있습니다. 트래픽이 커지면 그때 Postgres·KV 등으로 옮기면 됩니다.

031단계 — 분야별 RSS로 뉴스 모으기

분야마다 피드를 여러 개 등록할 수 있게 설계하면, 나중에 소스를 바꾸거나 추가하기 쉽습니다.

카테고리마다 "RSS 주소 + 이 주소의 출처 이름"을 짝지어 배열로 관리합니다. 예를 들어 AI 분야는 이렇게 구성했습니다.

// src/lib/categories.ts
export const CATEGORIES = [
  {
    key: "ai",
    label: "AI",
    emoji: "🤖",
    feeds: [
      { url: "https://www.aitimes.com/rss/allArticle.xml", source: "AI타임스" },
      { url: "http://rss.etnews.com/04046.xml", source: "전자신문" },
      { url: "http://rss.etnews.com/04.xml", source: "전자신문" },
    ],
  },
  // ... IT, 경제는 직접 지정한 피드, 정치·세계·스포츠·연예는
  // 아직 Google News RSS로 유지 (source를 안 적으면 제목의
  // "헤드라인 - 출처" 패턴에서 파싱)
];

수집 스크립트는 카테고리마다 등록된 피드를 전부 병렬로 가져온 뒤, 링크(URL)를 해시한 값을 id로 써서 중복을 제거합니다. 이미 오늘 저장된 기사와 새로 가져온 기사를 합칠 때, 같은 id가 있으면 새로 추가하지 않습니다.

// scripts/collect-news.ts (핵심만 발췌)
function articleId(link) {
  return crypto.createHash("sha1").update(link).digest("hex").slice(0, 16);
}

const existing = await readArticlesForDate(today);      // 오늘 이미 저장된 기사
const existingById = new Map(existing.map(a => [a.id, a]));

for (const article of 새로_수집한_기사들) {
  if (!existingById.has(article.id)) {
    existingById.set(article.id, article);               // 새 기사만 추가
  }
}
"오늘" 파일은 어느 시간대 기준인가

서버(GitHub Actions 러너)는 UTC로 돕니다. 그런데 사용자는 한국 시간(KST)으로 "오늘"을 생각합니다. 그래서 파일 이름을 정할 때는 new Date().toISOString()이 아니라, KST로 변환한 날짜 문자열을 직접 계산해서 씁니다 — 이 부분을 대충 넘어가면 7장에서 다루는 버그로 이어집니다.

카테고리별로 최대 개수를 정해두고(여기선 80건) 발행일 기준 최신순으로 잘라내면, 파일이 무한정 커지는 걸 막을 수 있습니다.

042단계 — 분야별로 화면에 보여주기

Next.js 서버 컴포넌트에서 파일을 직접 읽으면, 별도 API 없이 화면을 만들 수 있습니다.

화면(src/app/page.tsx)은 서버 컴포넌트 안에서 fs로 최근 며칠 치 JSON을 읽어 합친 뒤, 카테고리별로 나눠 보여줍니다. 데이터가 파일이라 별도 API 라우트 없이 바로 읽을 수 있는 게 이 구조의 장점입니다.

export default async function Home() {
  const articles = await readRecentArticles(2);   // 최근 2일치 KST 날짜 파일을 합침
  const trending = extractTrendingKeywords(articles, 12);
  // ... CATEGORIES를 순회하며 분야별 섹션 렌더링
}

급상승 키워드는 형태소 분석기 없이, 제목을 공백 기준으로 쪼개고 불용어를 거른 뒤 등장 빈도를 세는 단순한 방식으로 뽑습니다. 정교하진 않지만 "오늘 여러 매체에서 반복되는 단어"를 잡아내는 데는 이 정도로도 충분합니다.

배포 후 화면이 자동으로 갱신되는 이유

페이지는 export const revalidate = 3600으로 정적 생성됩니다. 데이터 자체는 GitHub Actions가 새로 커밋해야 바뀌므로, "커밋 → Vercel 재배포 → 새 정적 페이지"가 곧 갱신 주기입니다. 즉 이 페이지의 신선도는 revalidate 값이 아니라 수집 워크플로우 주기(2시간)가 사실상 결정합니다.

053단계 — Claude로 요약해 Discord로 보내기

기사 본문 전체가 아니라 제목 목록만 넘겨도, 오늘의 핵심 이슈를 뽑아내는 데는 충분합니다.

분야별로 그날 모인 기사 제목을 최대 25개까지 모아 Claude(claude-haiku-4-5)에 넘기고, 3~5개의 불릿으로 요약해달라고 요청합니다. 본문을 긁어오지 않아도 되니 구조가 단순해집니다.

// scripts/send-discord-digest.ts (핵심만 발췌)
const message = await client.messages.create({
  model: "claude-haiku-4-5-20251001",
  max_tokens: 400,
  messages: [{
    role: "user",
    content: `다음은 오늘 "${label}" 분야 뉴스 제목 목록이다.
중복·비슷한 내용은 묶어서, 가장 중요한 이슈 3~5개를 한국어 불릿(-)으로
간결하게 요약해줘. 각 불릿은 한 줄, 서두 설명 없이 핵심만.

${titles.join("\\n")}`,
  }],
});

Discord로는 분야별 Embed 하나씩(제목=이모지+분야명, 설명=요약+대표 링크 3개) 묶어서 한 번의 Webhook 호출로 보냅니다. Discord Embed는 메시지 하나에 최대 10개까지 넣을 수 있어, 카테고리 6~7개 정도는 여유 있게 들어갑니다.

await fetch(webhookUrl, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    content: `📰 **${today} 오늘의 뉴스 브리핑**`,
    embeds: [트렌드_키워드_embed, ...분야별_embed_목록],
  }),
});

064단계 — GitHub Actions로 자동 실행하기

워크플로우 파일 두 개가 각각 다른 주기로 돕니다. 하나는 데이터를 모으고, 하나는 그 데이터를 읽어 보냅니다.

# .github/workflows/collect-news.yml
on:
  schedule:
    - cron: "0 */2 * * *"       # 2시간마다
  workflow_dispatch: {}          # 수동 실행 버튼도 함께 열어둔다

permissions:
  contents: write                 # 워크플로우가 직접 커밋·푸시하려면 필요

jobs:
  collect:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx tsx scripts/collect-news.ts
      - name: Commit and push if changed
        run: |
          git config user.name "news-bot"
          git config user.email "news-bot@users.noreply.github.com"
          git add data/news
          git diff --cached --quiet || git commit -m "chore: collect news $(date -u +%FT%TZ)" && git push

다이제스트 쪽은 cron: "0 12 * * *" — UTC 12시 = KST 21시입니다. GitHub Actions의 cron은 항상 UTC 기준이라는 걸 기억해두면 스케줄을 헷갈리지 않습니다.

Secrets는 어디서 오는가

다이제스트 워크플로우가 쓰는 DISCORD_WEBHOOK_URL, ANTHROPIC_API_KEY는 코드에 적지 않고, 저장소 Settings → Secrets and variables → Actions에 등록한 값을 secrets.DISCORD_WEBHOOK_URL 형태로 불러 씁니다. 등록 방법은 GitHub Secrets · Vercel 환경변수 등록하기에서 다룹니다.

새 워크플로우를 만들면 스케줄이 실제로 실행될 때까지 기다리는 대신, workflow_dispatch를 열어두고 gh workflow run collect-news.yml로 바로 수동 실행해서 확인하는 게 훨씬 빠릅니다.

07실전에서 만난 함정 — KST/UTC 날짜 버그

실제로 이 프로젝트를 만들면서 겪은 버그입니다. 화면을 프로덕션 빌드까지 마쳤는데, 자정 근처 시간대에 기사가 전부 사라지는 문제가 있었습니다.

버그

"오늘 기사"를 UTC 문자열과 KST 문자열로 비교했다

화면에서 "오늘 수집된 기사만" 보여주려고, 기사의 pubDate(UTC ISO 문자열)가 kstDateString()(KST 기준 "YYYY-MM-DD")로 시작하는지 검사했다. 그런데 한국은 UTC보다 9시간 빠르므로, KST로는 이미 다음 날인데 UTC 문자열은 아직 전날 날짜로 남아있는 시간대가 매일 9시간씩 존재한다.

날짜 문자열을 비교할 땐 두 값이 같은 시간대 기준인지부터 확인해야 합니다. 이 프로젝트처럼 "파일은 KST로 나누고, 타임스탬프는 UTC로 저장한다"는 조합은 흔하지만, 그만큼 이런 어긋남이 생기기 쉽습니다.

해결

날짜로 다시 거르지 않고, 파일 자체를 신뢰했다

애초에 readRecentArticles()가 파일 이름 자체가 이미 KST 날짜 기준으로 나뉘어 있으므로, 읽어온 결과를 다시 문자열 비교로 거를 필요가 없었다. 화면 컴포넌트에서 중복 필터링 코드를 통째로 지우고, 파일 단위로 이미 걸러진 데이터를 그대로 썼다.

가장 안전한 시간대 버그 수정은 "변환을 더 정확히 하는 것"이 아니라, 애초에 시간대 변환이 필요한 지점 자체를 줄이는 것입니다. 데이터를 저장할 때 이미 한 번 KST로 정리해뒀다면, 읽는 쪽에서 또 변환·비교할 필요가 없습니다.

08체크리스트

만들 때 지킬 것

  • 링크 해시로 중복을 제거한다같은 기사가 여러 피드에 겹쳐 올라와도(예: 전자신문 04046과 04) 한 번만 저장된다.
  • 날짜 기준 시간대를 한 곳에서만 계산한다파일을 나눌 때 KST로 한 번 정리했다면, 읽는 쪽에서 다시 변환·비교하지 않는다.
  • 워크플로우에 workflow_dispatch를 열어둔다스케줄이 돌 때까지 기다리지 않고 바로 수동 실행해서 검증할 수 있다.
  • Secrets는 코드가 아니라 저장소 설정에 둔다레포에는 .env.example만 남기고, 실제 값은 Actions Secrets와 로컬 .env(gitignore)에만 존재한다.

흔한 실수

  • UTC로 저장한 타임스탬프를 KST 날짜 문자열과 그대로 비교하기7장에서 다룬 버그. 자정 근처 몇 시간 동안 데이터가 통째로 안 보이게 된다.
  • 모든 기사 본문을 통째로 LLM에 넣기제목만으로도 "오늘의 핵심 이슈" 요약엔 충분하고, 비용과 실패 지점(스크래핑 실패, 페이월)을 줄일 수 있다.
  • cron을 로컬 시간 기준으로 착각하기GitHub Actions의 cron은 항상 UTC. "매일 21시(KST)"는 0 12 * * *로 적어야 한다.
