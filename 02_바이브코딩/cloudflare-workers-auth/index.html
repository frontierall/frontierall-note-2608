배포한 정적 사이트에 로그인 걸기

Cloudflare Workers에 정적 사이트를 올리면 주소를 아는 사람은 누구나 열 수 있습니다. 개인 메모처럼 나만 봐야 하는 사이트라면 앞단에 로그인을 세워야 합니다. 이 자료는 방법을 비교하고, 그중 카드 등록 없이 되는 방식(Worker가 직접 인증)을 처음부터 끝까지 따라 하도록 정리한 것입니다.

  • 정적 파일에 "로그인 화면만 붙이는" 방식이 왜 보안이 아닌지
  • Cloudflare Access와 Worker 자체 인증 중 무엇을 고를지
  • assets.run_worker_first로 정적 파일 앞에 인증 코드 세우기
  • 비밀번호를 저장소에 남기지 않고 주입하는 방법(Workers Secrets)
  • 정말 막혔는지 curl로 확인하는 법

1. 먼저 알아야 할 것 — 화면만 가리는 건 자물쇠가 아니다

가장 흔히 떠올리는 방법은 페이지 안에 로그인 화면을 넣고, 자바스크립트로 통과했을 때만 내용을 보여주는 것입니다. Firebase Auth를 붙이는 방식도 여기에 해당합니다. 이건 자물쇠가 아니라 자물쇠 그림입니다.

브라우저가 자바스크립트를 실행하려면 HTML을 먼저 내려받아야 합니다. 그 시점에 파일은 이미 전달이 끝난 상태이고, 로그인 화면은 그 뒤에 그려질 뿐입니다. 그래서 브라우저를 거치지 않는 요청 한 줄이면 그대로 내용이 나옵니다.

curl https://<워커이름>.<계정서브도메인>.workers.dev/

로그인 화면은 뜨지 않고 본문 HTML이 그대로 출력됩니다. 막으려면 파일이 나가기 전에, 서버 쪽에서 판단해야 합니다.

2. 방법 비교

방법결제수단실제 차단코드
Cloudflare Access (Zero Trust)필요 (청구 $0)O없음
Worker 자체 인증불필요O약 30줄
Firebase Auth를 페이지에 삽입불필요X — 못 막음중간
Firebase + 서버에서 토큰 검증Blaze 필요O많음

2-1. Cloudflare Access — 코드는 0줄, 대신 카드 등록

Cloudflare가 사이트 앞단에서 로그인을 강제하는 방식입니다. 애플리케이션 코드를 한 줄도 건드리지 않고, *.workers.dev 주소에도 걸 수 있습니다. 다만 Zero Trust를 처음 켤 때 결제수단을 요구합니다. 공식 문서의 표현은 이렇습니다.

Complete your onboarding by selecting a subscription plan and entering your payment details. If you chose the Zero Trust Free plan, this step is still needed but you will not be charged.

즉 카드는 등록하되 요금은 청구되지 않습니다(Free는 50명까지). 카드 등록이 부담이 아니라면 이 방법이 가장 간단합니다. 설정은 Workers & Pages → 해당 Worker → Access 탭 → Protect this Worker behind Access에서 하고, 이때 All traffic을 골라야 합니다. Previews only를 고르면 정작 본 사이트는 그대로 열려 있습니다.

Worker 단위로 걸면 그 Worker에 붙은 모든 주소(workers.dev, 프리뷰, 나중에 붙일 커스텀 도메인)가 한꺼번에 보호됩니다. 반면 호스트명 하나만 지정하는 방식은 나중에 커스텀 도메인을 붙였을 때 그 주소가 뚫린 채로 열립니다.

2-2. Firebase는 이 용도에 맞지 않는다

카드 등록을 피하려고 Firebase를 떠올리기 쉽지만, 결론은 이렇습니다.

  • 클라이언트에 Auth만 붙이는 것 — 위 1번에서 본 대로 못 막습니다.
  • 서버에서 토큰을 검증하는 것 — Cloud Functions/Cloud Run이 필요하고 Blaze 플랜 = 결제수단 등록입니다. 같은 카드를 등록하면서 코드만 훨씬 많아집니다.
  • 내용을 Firestore에 저장하고 보안 규칙으로 막는 것 — 카드 없이 되지만, "폴더=카테고리, 파일=노트"인 정적 저장소 구조를 통째로 버리게 됩니다.

3. Worker 자체 인증 — 정적 파일 앞에 코드 세우기

핵심은 assets.run_worker_first 한 줄입니다. 이걸 켜면 정적 파일을 내보내기 전에 내 코드가 먼저 실행됩니다.

// wrangler.jsonc
{
  "name": "<워커이름>",
  "compatibility_date": "2026-08-29",
  "main": "./worker/index.js",
  "assets": {
    "directory": "./",
    "binding": "ASSETS",
    "run_worker_first": true
  }
}

워커의 뼈대는 이렇습니다. 쿠키가 유효하면 ASSETS 바인딩으로 넘기고, 아니면 로그인 화면으로 보냅니다.

export default {
  async fetch(request, env) {
    const url = new URL(request.url);

    if (url.pathname === '/login') {
      return request.method === 'POST'
        ? handleLogin(request, env)
        : loginPage();
    }

    if (await isAuthenticated(request, env)) {
      return env.ASSETS.fetch(request);   // 통과 → 정적 파일
    }

    const next = encodeURIComponent(url.pathname + url.search);
    return Response.redirect(new URL('/login?next=' + next, url), 302);
  },
};

3-1. 쿠키는 서명해서 발급한다

비밀번호가 맞으면 만료시각과 그 시각의 HMAC 서명을 쿠키에 담습니다. 서명이 있어야 사용자가 쿠키를 위조해 만료를 늘리는 것을 막을 수 있습니다.

const expires = Date.now() + 14 * 24 * 60 * 60 * 1000;
const token = expires + '.' + await sign(String(expires), env.AUTH_SECRET);

// Set-Cookie 헤더
// note_session=<token>; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1209600

HttpOnly는 자바스크립트가 쿠키를 못 읽게 하고, Secure는 HTTPS에서만 전송되게 합니다.

3-2. 비밀번호 비교는 시간차를 남기지 않는다

a === b로 비교하면 앞글자가 몇 개 맞았는지에 따라 응답 시간이 미세하게 달라집니다. 양쪽을 HMAC으로 한 번 씌운 뒤 바이트를 비교하면 길이와 내용이 모두 가려집니다.

const [ha, hb] = await Promise.all([
  crypto.subtle.sign('HMAC', key, enc.encode(a)),
  crypto.subtle.sign('HMAC', key, enc.encode(b)),
]);
const x = new Uint8Array(ha), y = new Uint8Array(hb);
let diff = 0;
for (let i = 0; i < x.length; i++) diff |= x[i] ^ y[i];
return diff === 0;

3-3. 로그인 후 돌아갈 주소는 검증한다

?next=를 그대로 Location에 넣으면 오픈 리다이렉트가 됩니다. 공격자가 ?next=//evil.com이 담긴 링크를 뿌리면, 우리 로그인 화면을 거쳐 외부 사이트로 튕겨 보낼 수 있습니다. 같은 사이트의 절대 경로만 허용합니다.

function safeNext(value) {
  const next = String(value ?? '');
  if (!next.startsWith('/') || next.startsWith('//')) return '/';
  if (next.startsWith('/login')) return '/';   // 로그인 무한루프 방지
  return next;
}

4. 비밀번호는 저장소에 두지 않는다

비밀번호와 서명키는 Workers Secrets로 주입합니다. 코드에도, 저장소에도 남기지 않습니다.

npx wrangler secret put NOTE_PASSWORD
npx wrangler secret put AUTH_SECRET

대시보드에서도 됩니다 — Workers & Pages → 해당 Worker → Settings → Variables and Secrets → Add에서 타입을 반드시 Secret으로 고릅니다(Text로 넣으면 값이 화면에 그대로 보입니다). 대시보드 Git 연동으로 배포한 경우라면 wrangler login 없이 이 방법이 더 간단합니다.

AUTH_SECRET은 사람이 정하는 비밀번호가 아니라 쿠키 서명키입니다. 외우기 쉬운 문자열을 쓰면 서명이 약해지므로 무작위 값을 씁니다.

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

로컬에서 wrangler dev로 시험할 때는 .dev.vars 파일을 쓰되 반드시 .gitignore에 넣습니다. 아래 값은 설명용 가짜 값입니다. 그대로 쓰지 않습니다.

# .dev.vars  ← .gitignore 에 반드시 추가
NOTE_PASSWORD=여기에-로컬-시험용-임시값
AUTH_SECRET=여기에-무작위-16진수-문자열

실제로 쓸 값은 오직 Workers Secrets에만 넣습니다.

5. 배포 순서 — 시크릿 먼저, push 나중

Git 연동 배포는 main에 push하는 순간 자동 재배포됩니다. 그래서 순서를 지키지 않으면 사이트가 통째로 죽습니다.

  1. 시크릿 2개 등록 (NOTE_PASSWORD, AUTH_SECRET)
  2. 그다음에 git push
  3. 배포 후 curl로 차단 확인

시크릿 없이 먼저 push하면, 워커가 시크릿을 찾지 못해 모든 경로가 500을 냅니다. 열리는 것이 아니라 안 열립니다. 코드에 이 상황을 명시적으로 처리해 두면 원인을 바로 알 수 있습니다.

if (!env.NOTE_PASSWORD || !env.AUTH_SECRET) {
  return new Response('시크릿이 등록되지 않았습니다.', { status: 500 });
}

6. 정말 막혔는지 확인하기

브라우저는 이미 로그인 쿠키를 갖고 있어서 "내 브라우저에서 열리네"는 확인이 되지 않습니다. 쿠키가 없는 curl로 봐야 합니다.

curl -s -o /dev/null -w "%{http_code} -> %{redirect_url}\n" \
  https://<워커이름>.<계정서브도메인>.workers.dev/
확인 항목기대 결과
쿠키 없이 최상위302 → /login
쿠키 없이 내부 파일 직접 요청302 → /login
틀린 비밀번호401
맞는 비밀번호302 + Set-Cookie
발급받은 쿠키로 재요청200 (본문)
위조한 쿠키302 → /login
?next=//evil.com/ 로 차단

200이 뜨면 실패입니다. 그 자리에서 내용이 새고 있다는 뜻입니다.

7. 겪게 되는 함정 둘

7-1. wrangler dev가 무한 재시작한다

assets.directory를 저장소 루트("./")로 두면, wrangler가 자기 작업 폴더 .wrangler/를 정적 파일로 감시하다가 스스로를 계속 재시작시킵니다. 로그에 Reloading local server...가 끝없이 찍힙니다.

.assetsignore로는 해결되지 않습니다. 그 파일은 업로드에서 제외할 뿐 dev의 파일 감시는 막지 않습니다. 상태 폴더를 프로젝트 밖으로 빼야 합니다.

npx wrangler dev --persist-to ../.wrangler-state

그와 별개로 .assetsignore는 워커 소스와 설정이 정적 파일로 공개되지 않도록 넣어 둡니다.

# .assetsignore (.gitignore 와 같은 형식)
worker
wrangler.jsonc
.assetsignore
.wrangler
.dev.vars

7-2. .html 요청에 307이 뜬다

정적 파일 라우터가 확장자를 떼면서 보내는 정상 동작이며 인증과 무관합니다. curl -L로 따라가면 최종 200이 나옵니다. 인증이 깨진 것으로 오해하기 쉬우니 구분해서 봅니다.

8. 이 방식의 한계 — 언제 갈아탈까

읽기 전용 개인 메모라면 이 정도로 충분합니다. 다만 아래는 감안하고 씁니다.

  • 비밀번호 하나를 공유하는 방식입니다. 새면 아는 사람은 모두 들어옵니다. 2단계 인증도 없습니다.
  • 무차별 대입 방어가 약합니다. 실패 시 지연을 주는 정도이므로, 짧은 비밀번호는 쓰지 않습니다.
  • 누가 언제 들어왔는지 기록이 남지 않습니다.

남과 공유해서 사람별 권한이 필요해지거나, 접속 기록이 남아야 하거나, 유출되면 곤란한 내용이 들어가는 시점이 갈아탈 때입니다. 그때는 Cloudflare Access로 옮기고 워커 인증 코드를 지우면 됩니다. 정적 파일 구조는 그대로라서 되돌리는 비용이 거의 없습니다.
