Railway가 무엇인가

앞서 본 네 가지 서비스(GitHub Pages · Netlify · Vercel · Cloudflare Pages)는 전부 "화면(정적 파일)"을 올리는 곳이었습니다. Railway(레일웨이)는 다른 종류의 서비스입니다. 서버 프로그램과 데이터베이스를 올리는 곳입니다. FastAPI·Flask·Express 같은 백엔드, Streamlit 앱, LangChain으로 만든 에이전트 서버, 그리고 PostgreSQL·Redis 같은 DB를 클릭 몇 번으로 인터넷에 띄웁니다. PART 06·07에서 파이썬 서버가 필요해지는 순간, 가장 먼저 손이 가는 도구입니다.

  • 정적 호스팅과 Railway가 근본적으로 무엇이 다른지
  • Project · Service · Variables — 세 가지 핵심 개념
  • 실습 — FastAPI 서버 올리기, DB 붙이기, CLI로 다루기
  • 요금이 "무료 플랜"이 아니라 사용량 과금이라는 점과 대응법
  • Render · Fly.io · Supabase와 언제 무엇을 고르는지
  • 수업에서 실제로 자주 막히는 지점과 해결법

1. 한 줄로 말하면

Railway는 GitHub에 올린 서버 코드를 자동으로 빌드해서 "항상 켜져 있는 서버"로 실행해 주고, 옆에 데이터베이스까지 클릭 한 번으로 붙여 주는 서비스입니다. 2020년에 시작했고, 한때 이 분야의 표준이었던 Heroku가 2022년 무료 플랜을 없애면서 그 자리를 이어받은 서비스 중 가장 많이 쓰이는 축에 듭니다. 서버·네트워크 설정을 몰라도 코드만 있으면 된다는 점에서 "백엔드계의 Vercel"이라고 이해하면 빠릅니다.

1-1. 정적 호스팅과 무엇이 다른가

정적 호스팅 (앞의 네 가지)Railway
올리는 것HTML·CSS·JS·이미지 파일실행 중인 프로그램 (파이썬·Node 등)
동작 방식파일을 CDN에 복사해 두고 그대로 전달서버 프로세스가 항상 켜진 채 요청을 처리
데이터베이스없음 (Supabase 등 외부 연결)같은 곳에 클릭 한 번으로 생성
오래 걸리는 작업·웹소켓·백그라운드불가 또는 제한적가능
요금무료 플랜 있음사용량 과금 (켜 둔 시간만큼)

위는 파일을 건네주고 끝, 아래는 서버가 켜져 있으면서 매번 계산하고 DB를 읽고 씁니다

1-2. "Vercel Functions로도 API 만들 수 있지 않나요?"

맞습니다. 요청 하나 받아서 몇 초 안에 답하는 API라면 Vercel·Netlify·Cloudflare의 함수로 충분합니다. Railway가 필요해지는 건 아래 중 하나가 생길 때입니다.

  • 파이썬으로 짠 서버 — LangChain·FastAPI·Streamlit은 파이썬이 편한데, 정적 호스팅의 함수는 대부분 JS 중심입니다
  • 한 요청이 몇 분씩 걸리는 작업 — 함수 실행 시간 제한(수십 초)에 걸립니다
  • 상태를 기억해야 하는 것 — 웹소켓 연결, 메모리에 올려 둔 모델, 백그라운드 큐
  • DB를 바로 옆에 두고 싶을 때 — PostgreSQL·Redis를 같은 프로젝트 안에

2. 핵심 개념 세 가지

Railway 대시보드를 열면 빈 캔버스가 나옵니다. 여기에 상자를 하나씩 놓는 방식인데, 상자의 종류가 곧 개념입니다.

개념뜻예
Project캔버스 하나 = 서비스 하나의 묶음"나의 RAG 챗봇"
Service캔버스 위의 상자 하나 = 실행 중인 프로그램 하나FastAPI 서버, PostgreSQL, 백그라운드 워커
Variables서비스마다 갖는 환경 변수. 다른 서비스의 값을 참조할 수 있음DATABASE_URL=${{Postgres.DATABASE_URL}}

같은 Project 안의 서비스들은 프라이빗 네트워크로 묶여서, 인터넷을 거치지 않고 서로 통신합니다. DB는 외부에 열지 않고 내 서버만 접근하게 두는 것이 기본입니다. 그리고 Project마다 Environment(production, 그리고 PR마다 자동 생성되는 임시 환경)가 따로 있어서, 실서비스를 건드리지 않고 시험할 수 있습니다.

캔버스(Project) 위의 상자(Service)들이 참조 변수로 서로를 가리킵니다

3. 실습 A — FastAPI 서버 올리기

파일 두 개면 됩니다. GitHub 저장소에 아래를 올려 두세요.

# main.py
import os
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def hello():
    return {"message": "안녕하세요, Railway!"}

# requirements.txt
fastapi
uvicorn
  1. railway.com에 GitHub 계정으로 가입합니다.
  2. New Project → Deploy from GitHub repo에서 저장소를 고릅니다.
  3. Railway가 requirements.txt를 보고 파이썬 프로젝트임을 알아채고 빌드를 시작합니다. (이 자동 감지 도구가 Railpack, 예전 이름 Nixpacks입니다.)
  4. 서비스 상자를 클릭 → Settings → Deploy → Start Command에 실행 명령을 넣습니다.
  5. Settings → Networking → Generate Domain을 누르면 이름.up.railway.app 주소가 생깁니다.
# Start Command
uvicorn main:app --host 0.0.0.0 --port $PORT

네 번째 단계의 명령 한 줄에서 사고의 대부분이 납니다

가장 많이 막히는 곳 — $PORT: Railway는 "이 번호로 서버를 열어라"를 PORT 환경 변수로 알려 줍니다. 로컬에서 하던 대로 --port 8000이라고 고정하면, Railway는 다른 번호를 기다리고 있으니 "Application failed to respond"가 뜹니다. 반드시 $PORT를 쓰고, 주소도 127.0.0.1이 아니라 0.0.0.0으로 여세요.

4. 실습 B — 데이터베이스 붙이기

  1. 캔버스에서 + New → Database → PostgreSQL을 누릅니다. 몇 초 뒤 DB 상자가 생기고, DATABASE_URL 같은 접속 정보가 그 상자의 Variables에 자동으로 채워집니다.
  2. 내 FastAPI 서비스 상자 → Variables → + New Variable에서 이름 DATABASE_URL, 값 ${{Postgres.DATABASE_URL}}을 넣습니다. 값을 복사해 붙이는 게 아니라 참조하는 것이라, DB 비밀번호가 바뀌어도 자동으로 따라갑니다.
  3. 코드에서는 환경 변수로 읽습니다.
# main.py 에 추가
import os
DATABASE_URL = os.environ["DATABASE_URL"]   # Railway가 넣어 준 값

DB 상자를 클릭하면 Data 탭에서 테이블을 직접 보고 고칠 수 있어, 별도 DB 도구 없이도 수업 실습이 가능합니다. Redis·MySQL·MongoDB도 같은 방법으로 붙습니다.

5. 실습 C — 터미널에서 CLI로 다루기

# 설치 · 로그인
npm i -g @railway/cli
railway login

# 현재 폴더를 Railway 프로젝트와 연결
railway init          # 새 프로젝트
railway link          # 이미 있는 프로젝트

# 지금 폴더를 그대로 배포 (Git 없이도 됨)
railway up

# 클라우드의 환경 변수를 주입해서 로컬에서 실행
railway run python main.py

# 로그 보기 · 변수 보기
railway logs
railway variables

railway run이 특히 유용합니다. .env 파일을 따로 만들지 않아도 Railway에 등록한 DATABASE_URL이나 OPENAI_API_KEY를 그대로 쓰면서 내 컴퓨터에서 테스트할 수 있습니다. Claude Code 같은 AI 코딩 도구에게 "Railway에 배포해 줘"라고 하면 대개 이 명령들을 씁니다.

6. 알아 두면 좋은 기능

  • 템플릿 — n8n, PostgreSQL + pgvector, Redis, Metabase 같은 것을 원클릭으로 띄웁니다. PART 07에서 벡터 DB가 필요할 때 pgvector 템플릿이 바로 쓰입니다.
  • PR 환경 — PR을 열면 그 브랜치만의 임시 환경(서비스 + DB 복제)이 자동으로 생기고, 닫으면 사라집니다.
  • 롤백 — Deployments 목록에서 이전 배포의 Redeploy를 누르면 그 시점으로 돌아갑니다.
  • 로그·메트릭 — CPU·메모리·네트워크 사용량 그래프와 실시간 로그가 대시보드에 있습니다. 요금이 사용량 기준이라 이 그래프를 자주 보게 됩니다.
  • App Sleeping — 요청이 없으면 서비스를 재워서 비용을 아낍니다. 수업용 서버는 켜 두면 좋습니다. (첫 요청은 깨어나느라 몇 초 느립니다.)
  • Cron — 서비스를 "매일 9시"처럼 주기적으로만 실행할 수 있습니다.
  • Dockerfile — 저장소에 있으면 자동 감지 대신 그걸로 빌드합니다. 특수한 환경이 필요할 때의 탈출구입니다.
  • Volume — 컨테이너는 재배포할 때 안의 파일이 사라집니다. 업로드된 파일처럼 남겨야 하는 것은 Volume에 둡니다. (DB 서비스는 자동으로 Volume이 붙어 있습니다.)

7. 요금 — "무료 플랜"이 아니라 "사용량 과금"

정적 호스팅과 가장 다른 지점이라 따로 짚습니다. Railway에는 영구 무료 플랜이 없습니다. 가입하면 한 번 쓰는 체험 크레딧을 주고, 그 뒤로는 Hobby 플랜(월 $5, 그 안에 $5어치 사용량 포함)부터 시작합니다. 사용량은 아래 네 가지로 계산됩니다.

항목무엇에 비례하나줄이는 법
CPUvCPU × 켜 둔 시간안 쓰는 서비스 삭제, App Sleeping
메모리GB × 켜 둔 시간큰 모델을 메모리에 올리지 않기
네트워크밖으로 나간 데이터 양큰 파일은 외부 스토리지에
VolumeGB × 월불필요한 데이터 정리

작은 FastAPI 서버 하나와 PostgreSQL 하나 정도는 대개 Hobby에 포함된 사용량 안에서 해결됩니다. 다만 "켜 둔 시간"에 비례하므로, 실습이 끝난 프로젝트를 그대로 두면 다음 달에도 계속 과금됩니다. 정확한 단가는 공식 요금 페이지에서 확인하세요.

수업에서 지키면 좋은 습관 세 가지: ① 대시보드의 Usage에서 사용량 알림을 켜 둔다. ② 실습이 끝난 프로젝트는 삭제하거나 서비스를 Remove한다. ③ 시험용 서버는 App Sleeping을 켠다. 정적 호스팅에 익숙해진 상태에서 "무료겠지" 하고 방치하는 것이 가장 흔한 사고입니다.

8. 비슷한 서비스와 비교

서비스성격이럴 때 고릅니다
Railway서버 + DB를 캔버스에 놓는 방식, 설정 최소파이썬 백엔드·에이전트 서버를 빨리 올리고 싶을 때
RenderRailway와 가장 비슷. 무료 티어 있음(요청 없으면 잠들고 깨는 데 수십 초)돈 안 들이고 먼저 시험해 보고 싶을 때
Fly.io전 세계 여러 지역에 배포, CLI 중심, 난이도 높음지연 시간이 중요하거나 인프라를 직접 다루고 싶을 때
Heroku이 분야의 원조. 2022년 무료 종료기존 자료·튜토리얼이 Heroku 기준일 때 참고용
SupabaseDB·로그인·파일 저장을 서비스로 제공. 내 서버 코드는 못 올림서버 없이 DB와 인증만 필요할 때 (PART 04)

헷갈리기 쉬운 건 Supabase와의 관계입니다. Supabase는 "DB를 빌려주는 곳", Railway는 "내 프로그램을 돌려주는 곳"입니다. 그래서 둘은 경쟁이 아니라 조합입니다 — 프론트는 Vercel, 서버는 Railway, DB는 Railway 안의 Postgres나 Supabase, 이렇게 나눠 올리는 구성이 흔합니다.

화면은 정적 호스팅에, 비밀이 필요한 서버와 DB는 Railway에 — 흔한 조합입니다

정리 기준: 화면만 있다 → 정적 호스팅 4종. DB·로그인만 필요하고 서버 코드는 없다 → Supabase. 파이썬 서버·오래 걸리는 작업·상시 실행 → Railway. 일단 무료로 → Render.

위에서부터 차례로 물어보면 대체로 답이 나옵니다

9. 자주 겪는 문제

9-1. "Application failed to respond"

거의 항상 PORT입니다. 3장의 인용구를 다시 보세요. 포트를 $PORT로, 호스트를 0.0.0.0으로. Node라면 app.listen(process.env.PORT || 3000)입니다.

9-2. 빌드는 됐는데 바로 죽는다 / Start Command를 모른다

Railway가 실행 명령을 추측하지 못한 경우입니다. Settings의 Start Command에 직접 넣거나, 저장소 루트에 railway.json으로 남겨 두면 코드와 함께 관리됩니다.

// railway.json (저장소 루트)
{
  "deploy": {
    "startCommand": "uvicorn main:app --host 0.0.0.0 --port $PORT"
  }
}

9-3. 로컬에서는 되는데 배포하면 모듈이 없다고 한다

requirements.txt(파이썬) 또는 package.json(Node)에 그 패키지가 빠져 있는 것입니다. 로컬에 pip install만 하고 파일에 안 적은 경우가 대부분입니다. pip freeze > requirements.txt로 맞추세요.

9-4. API 키가 없다고 한다

로컬 .env는 Railway에 올라가지 않습니다(올리면 안 됩니다). 서비스의 Variables 탭에 OPENAI_API_KEY 등을 직접 등록하세요. Raw Editor를 열면 .env 내용을 통째로 붙여 넣을 수 있습니다.

9-5. 업로드한 파일이 재배포 후 사라졌다

6장의 Volume 항목입니다. 컨테이너 안의 파일은 임시입니다. 남겨야 하는 파일은 Volume을 붙이거나 외부 스토리지(Supabase Storage, R2 등)에 두세요.

9-6. 어느 날 서비스가 꺼져 있다

체험 크레딧이 소진됐거나 플랜 한도에 닿은 것입니다. 대시보드 상단 배너와 Usage를 확인하세요. 7장의 습관 세 가지가 예방책입니다.

10. 정리

  • Railway = 서버 프로그램과 DB를 올리는 곳. 정적 호스팅 4종과는 역할이 다르다
  • 핵심 개념은 Project(캔버스) → Service(상자) → Variables(참조 변수)
  • 배포는 GitHub 연동 또는 railway up, DB는 + New → Database
  • 막히는 지점은 대개 $PORT, Start Command, requirements.txt, 환경 변수 네 가지
  • 무료 플랜이 없다 — 사용량 알림 켜기, 끝난 프로젝트 삭제하기
