PART 02 · 바이브코딩 교안

Claude Code로 구글 로그인 구현하기

실제 서비스(ClassShelf)에 Supabase Auth + Google OAuth를 붙이면서 겪은 과정을 그대로 정리한 실습 자료입니다. Google Cloud Console에서 OAuth 클라이언트를 만드는 화면 흐름과, Claude Code·Supabase CLI로 이를 서비스에 연결하며 실제로 마주친 오류들을 함께 다룹니다.

  • Google Cloud Console에서 OAuth 동의 화면(브랜딩)과 클라이언트 ID 발급
  • "승인된 JavaScript 원본"과 "승인된 리디렉션 URI"를 헷갈려서 난 오류
  • Supabase config.toml에 Google Provider 등록하고 배포하기
  • Supabase CLI 조직 인증이 꼬였을 때 다시 로그인하는 법

1. Google Cloud Console — OAuth 동의 화면 만들기

OAuth 클라이언트 ID를 만들려면 그 전에 Google 인증 플랫폼(브랜딩)이 구성되어 있어야 합니다. 아직 안 되어 있다면 클라이언트 생성 화면에서 바로 경고가 뜨고 진행이 막힙니다.

1-1. 사용자 인증 정보 페이지로 이동

Google Cloud 콘솔 좌측 메뉴에서 API 및 서비스 → 사용자 인증 정보로 들어갑니다.

API 및 서비스 → 사용자 인증 정보

1-2. OAuth 클라이언트 ID 만들기 시도

+ 사용자 인증 정보 만들기를 누르고 OAuth 클라이언트 ID를 선택합니다.

사용자 인증 정보 만들기 → OAuth 클라이언트 ID

실전 트러블슈팅: 프로젝트에 동의 화면이 한 번도 구성된 적이 없으면 "OAuth 클라이언트 ID를 만들려면 먼저 동의 화면을 구성해야 합니다"라는 경고가 뜨고 클라이언트 생성이 막힙니다. 아래처럼 동의 화면 구성 버튼부터 눌러 브랜딩을 먼저 완료해야 합니다.

동의 화면(브랜딩)이 없으면 클라이언트 생성이 막힌다

1-3. 브랜딩 마법사 진행

시작하기를 누르면 앱 정보 → 대상 → 연락처 정보 → 완료, 총 4단계로 구성된 마법사가 나옵니다.

Google 인증 플랫폼 — 시작하기

① 앱 정보 — 앱 이름과 사용자 지원 이메일을 입력합니다. (예: 앱 이름 ClassShelf, 지원 이메일은 서비스 관리자 계정)

① 앱 정보

② 대상 — 개인 프로젝트나 테스트 단계라면 외부를 선택합니다. (조직 내부 사용자만 쓸 경우에만 내부를 선택)

② 대상 — 외부

③ 연락처 정보 — 정책 관련 안내를 받을 이메일 주소를 입력합니다.

③ 연락처 정보

④ 완료 — Google API 서비스 사용자 데이터 정책 동의 체크박스를 체크하고 계속을 누릅니다.

④ 완료 — 정책 동의

네 단계 모두 체크 표시가 뜨면 만들기를 눌러 브랜딩을 완료합니다.

4단계 완료 → 만들기

2. OAuth 클라이언트 ID 발급

브랜딩이 끝나면 클라이언트 메뉴에서 실제 OAuth 클라이언트를 만들 수 있습니다.

2-1. 클라이언트 만들기

클라이언트 → + 클라이언트 만들기

2-2. 애플리케이션 유형 선택

Next.js처럼 서버가 리디렉션을 처리하는 웹 서비스라면 웹 애플리케이션을 선택합니다.

애플리케이션 유형 — 웹 애플리케이션

2-3. 승인된 JavaScript 원본 vs 승인된 리디렉션 URI

이 화면에서 가장 헷갈리기 쉬운 부분입니다. 두 필드는 용도가 완전히 다릅니다.

  • 승인된 JavaScript 원본 — 브라우저에서 직접 요청을 보낼 도메인의 origin만 입력합니다. 경로(/ 이후)나 끝의 슬래시를 포함할 수 없습니다. Supabase가 서버 쪽에서 리디렉션을 처리하는 구조라면 이 필드는 비워둬도 됩니다.
  • 승인된 리디렉션 URI — Google이 로그인 후 실제로 돌려보낼 전체 콜백 경로를 입력합니다. Supabase는 https://<project-ref>.supabase.co/auth/v1/callback 형태입니다.

승인된 리디렉션 URI에 Supabase 콜백 주소 입력 (전체 경로는 /auth/v1/callback까지 포함)

실전 트러블슈팅: 전체 콜백 경로(.../auth/v1/callback)를 실수로 승인된 JavaScript 원본 필드에 붙여넣으면 "올바르지 않은 출처: URI는 경로를 포함하거나 '/'로 끝날 수 없습니다" 오류가 납니다. JavaScript 원본은 경로 없는 origin 전용, 전체 경로는 반드시 리디렉션 URI 쪽에 입력해야 합니다.

2-4. 클라이언트 ID / 보안 비밀번호 확인

만들기를 누르면 클라이언트 ID와 클라이언트 보안 비밀번호(secret)가 한 번만 표시됩니다.

OAuth 클라이언트 생성 완료 — 이 화면을 벗어나면 보안 비밀번호를 다시 볼 수 없다

보안 주의: 클라이언트 보안 비밀번호는 서비스 전체의 Google 로그인을 대신할 수 있는 자격 증명입니다. 캡처 이미지나 대화창에 노출했다면 작업 후 재발급하고, 코드/커밋에는 절대 그대로 넣지 않습니다.

3. Supabase에 Google Provider 등록

발급받은 클라이언트 ID·비밀번호를 Supabase Auth에 등록해야 실제로 "Google로 로그인" 버튼이 동작합니다. 대시보드에서 직접 설정할 수도 있지만, 여기서는 supabase/config.toml을 코드로 관리하고 CLI로 배포합니다.

3-1. config.toml에 Provider 추가

[auth.external.google]
enabled = true
client_id = "527040890999-xxxxxxxxxxxxxxxxxxxxx.apps.googleusercontent.com"
# 절대 secret 값을 그대로 커밋하지 않는다 — 환경 변수로 치환
secret = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET)"
redirect_uri = ""
url = ""
skip_nonce_check = false

secret은 env(VAR_NAME) 문법으로 환경 변수를 참조하게 하고, 실제 값은 Supabase 프로젝트의 비밀 변수(secrets)로 별도 등록합니다.

supabase secrets set SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET="GOCSPX-..." --project-ref <project ref>

3-2. 원격 설정에 반영

supabase config push

실전 트러블슈팅: supabase init으로 갓 생성한 config.toml을 그대로 push하면, 건드리지 않은 값까지 로컬 기본값으로 덮어써 버릴 수 있습니다. 실제로 이 과정에서 email.max_frequency(메일 발송 최소 간격)와 email.enable_confirmations가 의도치 않게 바뀐 적이 있습니다. config push는 항상 명령이 보여주는 diff를 먼저 확인하고, 예상 밖의 변경이 있으면 되돌린 뒤 다시 push합니다.

3-3. Supabase CLI 인증이 다른 조직으로 붙어 있을 때

CLI가 원하는 조직이 아닌 다른 계정/조직에 로그인되어 있으면 config push, projects list 같은 명령이 403이나 엉뚱한 프로젝트 목록을 반환합니다. 이럴 때는 다시 로그인합니다.

supabase login

브라우저가 자동으로 열리고, 터미널에 표시된 인증 코드를 브라우저 쪽 화면에 입력해 CLI와 계정을 연결합니다.

supabase login — 터미널의 인증 코드를 브라우저에 입력해 CLI를 재인증한다

실전 트러블슈팅: Claude Code처럼 브라우저를 직접 열 수 없는(non-TTY) 환경에서는 supabase login을 에이전트가 대신 실행할 수 없습니다(LegacyLoginMissingTokenError: Cannot use automatic login flow inside non-TTY environments). 이런 경우 사용자가 터미널에서 직접 supabase login을 실행하고, 완료 후 supabase projects list로 올바른 조직/프로젝트가 보이는지 확인한 뒤 이어서 진행합니다.

4. 로그인 페이지에 Google 버튼 연결

Provider 등록이 끝나면, 클라이언트 코드에서는 Supabase Auth의 signInWithOAuth를 호출하는 Server Action 하나만 있으면 됩니다.

// app/login/actions.ts
"use server";

export async function signInWithGoogle() {
  const supabase = await createClient();
  const { data, error } = await supabase.auth.signInWithOAuth({
    provider: "google",
    options: { redirectTo: `${getSiteUrl()}/auth/callback` },
  });
  if (error) throw error;
  redirect(data.url);
}

버튼을 누르면 Google 로그인 화면 → 동의 → /auth/callback으로 리디렉션되어 세션이 생성됩니다. 콜백 라우트는 PKCE(?code=)와 구버전 implicit(#access_token=) 두 방식을 모두 받을 수 있게 만들어 두는 것이 안전합니다.

5. 검증

배포 후 실제로 Google Provider가 켜졌는지는 로그인 버튼을 눌러 리디렉션 URL의 client_id가 방금 발급한 값과 일치하는지 확인하면 됩니다.

curl -sI "https://<project-ref>.supabase.co/auth/v1/authorize?provider=google" | grep -i location

Location 헤더가 accounts.google.com으로 향하고, 그 안의 client_id 파라미터가 Google Cloud Console에서 발급받은 값과 같으면 정상입니다.

실수가 가장 잦은 지점은 두 곳입니다 — Google Cloud의 JavaScript 원본과 리디렉션 URI를 혼동하는 것, 그리고 Supabase CLI가 의도치 않은 조직/계정에 로그인되어 있는 것. 두 가지만 미리 알고 있으면 나머지 과정은 화면을 따라가는 것만으로 충분합니다.
