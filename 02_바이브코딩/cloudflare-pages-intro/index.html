Cloudflare Pages가 무엇인가

Cloudflare Pages는 Netlify·Vercel과 같은 부류의 정적 사이트 배포·호스팅 서비스입니다. GitHub 저장소를 연결하면 push할 때마다 자동으로 빌드해서 주소를 붙여 주죠. 다른 둘과의 결정적 차이는 만든 회사의 본업에 있습니다. Cloudflare는 원래 호스팅 회사가 아니라 전 세계 인터넷 트래픽의 상당 부분이 거쳐 가는 네트워크 회사이고, Pages는 그 거대한 네트워크 위에 내 사이트를 직접 얹어 두는 서비스입니다. 그래서 빠르고, 무료 플랜이 유난히 관대합니다.

  • Cloudflare가 어떤 회사이고, Pages가 그 안에서 어떤 위치인지
  • 이름이 헷갈리는 Pages와 Workers의 관계
  • 무료 플랜이 다른 서비스와 어떻게 다른지
  • 가장 빠른 배포 두 가지 — Git 연동, 폴더 직접 업로드
  • 알아 두면 좋은 기능(브랜치별 미리보기, Functions, _redirects)
  • 수업에서 실제로 자주 막히는 지점과 해결법

이 교안의 위치: 같은 파트의 Cloudflare Workers로 정적 사이트 배포하기가 실제 화면 캡처를 따라가는 실습 기록이라면, 이 교안은 그 전에 읽는 개념 편입니다. "Pages인지 Workers인지" 헷갈리는 이유도 여기서 풀어 둡니다.

1. 한 줄로 말하면

Cloudflare Pages는 Cloudflare의 전 세계 서버망(CDN) 위에 내 사이트 파일을 직접 올려 두고, GitHub과 연결해 자동으로 갱신해 주는 무료 호스팅 서비스입니다. 2020년 말에 나왔고, Netlify·Vercel이 먼저 만들어 둔 "Git 연동 자동 배포" 방식을 그대로 따르되, Cloudflare가 가진 네트워크 규모를 무기로 삼았습니다.

1-1. Cloudflare는 원래 무엇을 하는 회사인가

Cloudflare(2009년 창업)는 웹사이트 앞에 서서 세 가지 일을 대신해 주는 회사입니다.

역할쉽게 말하면
CDN사이트 파일을 전 세계 300개 넘는 도시의 서버에 복사해 두고, 접속한 사람과 가장 가까운 곳에서 응답
DNSmysite.com이라는 이름을 실제 서버 주소로 바꿔 주는 전화번호부 (1.1.1.1이 이 회사 것)
보안DDoS 공격·봇 트래픽을 사이트에 닿기 전에 걸러 냄

원래는 "내 서버는 따로 있고, Cloudflare는 그 앞을 지키는 방패"였습니다. Pages는 여기서 한 걸음 더 나가서 "서버를 아예 두지 말고 파일을 방패 안에 넣어 두자"는 발상입니다. 원본 서버가 없으니 느려질 곳도, 다운될 곳도 없습니다.

원본 서버가 없으니 느려질 곳도 다운될 곳도 없습니다

2. Pages와 Workers — 이름이 헷갈리는 이유

Cloudflare 대시보드에 들어가면 "Workers & Pages"라는 메뉴가 하나로 묶여 있고, 정작 새 프로젝트를 만들려고 하면 Workers 쪽으로 안내합니다. 처음 보면 혼란스러운데, 역사를 알면 간단합니다.

WorkersPages
등장2017년2020년
원래 용도CDN 서버에서 코드를 실행 (서버리스 함수)CDN 서버에서 정적 파일을 서빙 (사이트 호스팅)
지금2024년부터 Workers가 정적 파일 서빙도 흡수 (Workers Static Assets). 새 프로젝트는 Workers로 시작하도록 권장하고, 기존 Pages 프로젝트는 계속 지원

정리하면 "Pages = 정적 사이트 전용이던 서비스, Workers = 코드 실행 서비스였는데 이제 둘 다 하는 서비스"입니다. 이 교안에서 설명하는 개념(Git 연동, 브랜치별 미리보기, 무료 한도, _redirects)은 어느 쪽으로 배포하든 거의 그대로 적용됩니다. 인터넷에서 "Cloudflare Pages"로 검색해 나오는 자료도 대부분 여전히 유효합니다.

다만 방향은 분명합니다. Cloudflare는 Pages를 종료하는 게 아니라 Workers로 흡수하는 중이라, Secrets Store·Workflows·Containers 같은 새 기능은 Workers 전용으로만 나오고 Pages는 유지보수 수준의 업데이트에 머물러 있습니다. 새 프로젝트는 Workers(Static Assets)로 시작하는 것이 공식 권장 방향이고, 이미 있는 Pages 프로젝트는 당분간 그대로 정상 동작합니다.

대시보드가 Workers 쪽으로 안내하는 이유 — 정적 사이트도 이제 Workers가 서빙합니다

수업에서는: 실습은 Workers 배포 교안의 흐름(Workers & Pages → Create → Connect GitHub)을 따릅니다. 이 교안에서 "Pages"라고 부르는 것은 정적 사이트를 Cloudflare에 올리는 방식 전체를 가리킨다고 이해하면 됩니다.

3. 무료 플랜이 유난히 관대한 이유

Netlify·Vercel·GitHub Pages는 무료 플랜에 월 대역폭 한도(보통 100GB 안팎)가 있습니다. 사이트가 갑자기 유명해지면 한도를 넘겨 유료로 넘어가야 하죠. Cloudflare는 애초에 전 세계 트래픽을 처리하는 게 본업이라, 정적 파일 대역폭에 한도를 두지 않습니다.

항목Cloudflare 무료 플랜
정적 파일 대역폭·요청 수무제한 (HTML·CSS·JS·이미지)
동적 기능(Functions·SSR·미들웨어)Workers 무료 한도 적용 — 하루 10만 요청, 요청당 CPU 10ms
private 저장소 연결가능
상업적 사용가능 (Vercel Hobby는 불가)
사이트 수무제한
파일 1개 최대 크기 / 사이트당 파일 수25 MiB / 20,000개
월 빌드 횟수·시간월 500회, 빌드당 20분 타임아웃, 동시 빌드 1개

구체적인 숫자는 정책에 따라 바뀌므로 공식 한도 문서에서 확인하세요. 비공개 저장소·상업 사이트는 Netlify도 무료로 되지만, 정적 파일 대역폭이 무제한인 곳은 이 넷 중 Cloudflare뿐입니다.

"무제한"은 정적 파일 얘기입니다: 순수 HTML·CSS·JS 사이트라면 트래픽 걱정이 정말 없습니다. 하지만 API 라우트, 서버 렌더링, 로그인 처리처럼 Functions가 하나라도 들어가는 순간 그 요청은 Workers 무료 한도(하루 10만 요청)를 따릅니다. 바이브 코딩으로 만드는 결과물은 금방 후자로 넘어가니, "정적인 부분은 무제한, 동적인 부분은 하루 10만"으로 기억하세요. 빌드 500회도 혼자 쓸 땐 넉넉하지만, 팀원 여럿이 커밋마다 자동 빌드를 돌리면 생각보다 빨리 찹니다.

4. 실습 A — GitHub 연동 자동 배포

가장 표준적인 방법이고, 한 번 연결하면 push만으로 자동 배포됩니다. 실제 화면은 Workers 배포 교안에 캡처가 있으니, 여기서는 개념적 흐름만 짚습니다.

  1. dash.cloudflare.com 가입 후 이메일 인증을 먼저 마칩니다. (인증 전에는 프로젝트 생성이 막힙니다.)
  2. Workers & Pages → Create → Connect GitHub에서 Cloudflare 앱 권한을 승인하고 저장소를 고릅니다.
  3. 빌드 설정에서 Framework preset(자동 인식), Build command, Build output directory를 확인합니다.
  4. Deploy를 누르면 Initializing → Cloning → Installing → Deploying 순서로 진행되고, 끝나면 프로젝트.pages.dev(Workers 흐름이면 프로젝트.계정.workers.dev) 주소가 나옵니다.

4-1. 빌드 설정에서 볼 것은 두 칸

항목순수 HTMLReact(Vite)Next.js
Build command(비워 둠)npm run buildnpx @cloudflare/next-on-pages 또는 OpenNext 어댑터
Build output directory/ (또는 public)dist어댑터가 지정

Next.js는 주의: Vercel과 달리 Cloudflare에서 Next.js를 돌리려면 어댑터가 필요하고, 일부 기능은 제한됩니다. Next.js 프로젝트는 Vercel이 훨씬 편합니다. Cloudflare는 순수 HTML, Vite·Astro·SvelteKit 같은 정적 결과물이 나오는 프로젝트에서 가장 빛납니다.

5. 실습 B — 폴더 직접 업로드 (Git 없이)

Netlify의 드래그 앤 드롭처럼, Cloudflare도 Git 없이 완성된 폴더를 직접 올리는 방법이 있습니다. 두 가지입니다.

5-1. 대시보드에서 업로드

Workers & Pages → Create → Upload assets(또는 Pages → Direct Upload)를 선택하고 프로젝트 이름을 정한 뒤, 폴더를 끌어다 놓거나 zip 파일을 올립니다. 몇 초 뒤 주소가 생깁니다.

5-2. 터미널에서 wrangler CLI로 업로드

# 1) Cloudflare 로그인 (브라우저가 열림)
npx wrangler login

# 2) 완성된 폴더를 Pages 프로젝트로 배포
npx wrangler pages deploy ./dist --project-name=my-site

# (Workers 방식이면) 저장소 루트에 wrangler.jsonc를 두고
npx wrangler deploy

wrangler는 Cloudflare의 공식 명령줄 도구입니다. Claude Code 같은 AI 코딩 도구에게 "Cloudflare에 배포해 줘"라고 하면 대개 이 명령을 씁니다.

실전 트러블슈팅 — 이름은 처음에 정한다: 프로젝트 이름이 곧 주소(이름.pages.dev)가 되고, 나중에 바꾸기 어렵습니다. Netlify처럼 자유롭게 바꿀 수 없으니, 짧고 최종적인 이름으로 시작하세요. 자세한 사정은 Workers 배포 교안 5-3절에 있습니다.

6. 알아 두면 좋은 기능

6-1. 브랜치별 미리보기 주소

Git 연동 프로젝트는 main이 아닌 브랜치에 push하면 그 브랜치 전용 주소(브랜치.프로젝트.pages.dev)가 자동으로 생기고, 배포 하나하나에도 고유 주소(해시.프로젝트.pages.dev)가 붙습니다. Vercel의 Preview와 같은 개념이며, PR 화면에 링크가 댓글로 달립니다.

브랜치 이름이 주소 앞에 붙습니다 — 합치기 전에 눌러 볼 수 있습니다

6-2. Functions — 폴더 구조가 곧 API 주소

저장소에 functions/ 폴더를 만들면, 그 안의 파일 경로가 그대로 API 주소가 됩니다. 별도 설정이 없습니다.

// functions/api/hello.js  →  https://내사이트/api/hello
export function onRequest(context) {
  return Response.json({ message: "안녕하세요" });
}

대괄호 파일명([id].js)은 주소의 그 자리에 무엇이 와도 받아 줍니다

이 함수는 Workers 위에서 돌아가므로, 접속한 사람과 가장 가까운 Cloudflare 서버에서 실행됩니다. 그래서 요금·한도도 Workers 기준(무료: 하루 10만 요청)을 따릅니다. KV(키-값 저장소), D1(SQLite DB), R2(파일 저장소) 같은 Cloudflare의 다른 서비스를 여기에 붙일 수도 있는데, 이건 PART 07에서 필요해질 때 다시 다룹니다.

6-3. _redirects와 _headers

Netlify와 같은 형식의 두 파일을 배포 폴더에 두면 리다이렉트와 HTTP 헤더를 설정할 수 있습니다.

# _redirects
/old-page   /new-page   301
/blog/*     /posts/:splat   301

# _headers
/*
  X-Frame-Options: DENY

6-4. 커스텀 도메인 · 롤백 · 통계

  • 도메인 — 도메인의 DNS를 이미 Cloudflare에서 관리하고 있다면 클릭 두 번이면 연결됩니다. 다른 곳에서 산 도메인도 CNAME으로 연결 가능하며 HTTPS는 자동입니다.
  • 롤백 — Deployments 목록에서 이전 배포의 Rollback to this deployment를 누르면 즉시 되돌아갑니다.
  • Web Analytics — 쿠키 없는 방문자 통계가 무료로 포함됩니다.

대역폭까지 네 칸이 전부 열려 있는 곳은 Cloudflare뿐입니다 — 단, 정적 파일 기준 (숫자는 바뀔 수 있으니 공식 페이지 확인)

Cloudflare의 약점은 딱 하나, 대시보드가 복잡하다는 점입니다. CDN·DNS·보안·Workers·R2 등 수십 가지 서비스가 한 화면에 있어서, 처음에는 "정적 사이트 하나 올리는 메뉴"를 찾는 것부터 헤맵니다. Workers 배포 교안에서 검색창(⌘K)에 worker를 치라고 안내하는 이유가 그것입니다.

정리 기준: 트래픽 걱정 없이 무료로, 비공개 저장소로, 상업 사이트까지 → Cloudflare. Next.js → Vercel. Git이 낯설거나 폼이 필요 → Netlify. 순수 문서 → GitHub Pages.

8. 자주 겪는 문제

8-1. 배포는 성공했는데 화면이 비어 있음 / 404

Build output directory가 잘못된 경우가 대부분입니다. Vite는 dist, Create React App은 build, 순수 HTML은 /입니다. 배포 로그 끝부분에 "Found N files"가 0에 가깝다면 폴더를 잘못 가리킨 것입니다.

8-2. SPA(React·Vue)에서 새로고침하면 404

Pages는 배포 폴더에 404.html이 없으면 자동으로 SPA로 판단해 모든 경로에 index.html을 돌려줍니다. 즉 대부분은 아무것도 안 해도 됩니다. Workers 방식(wrangler.jsonc)이라면 아래 한 줄을 추가합니다.

// wrangler.jsonc
{
  "name": "my-site",
  "compatibility_date": "2026-09-01",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  }
}

8-3. 빌드 중 Node 버전 오류

Cloudflare 빌드 서버의 기본 Node 버전이 프로젝트와 안 맞을 때 생깁니다. Settings → Environment variables에 NODE_VERSION을 20처럼 넣거나, 저장소 루트에 .nvmrc 파일을 두면 그 버전으로 빌드합니다.

8-4. 로컬에서는 되는데 배포하면 이미지가 안 보임

다른 서비스와 같은 원인입니다. 빌드 서버(리눅스)는 파일명 대소문자를 구분합니다. Logo.png를 logo.png로 부르면 배포 후에만 깨집니다.

8-5. 이메일 인증 전에는 아무것도 못 만듦

가입만 하고 인증 메일 링크를 안 누르면 "Create application"이 막힙니다. 스팸함까지 확인하세요.

9. 정리

  • Cloudflare Pages = 세계 최대급 CDN 위에 사이트를 직접 올려 두는 무료 호스팅
  • Pages와 Workers는 지금 하나로 합쳐지는 중 — 개념은 같고, 새 프로젝트는 Workers 흐름으로
  • 무료 플랜의 강점: 대역폭 무제한 · private 저장소 · 상업 사용 가능
  • 시작은 GitHub 연동 또는 폴더 직접 업로드(wrangler pages deploy)
