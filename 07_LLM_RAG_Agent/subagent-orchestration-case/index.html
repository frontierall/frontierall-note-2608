01서브에이전트가 뭔가요

비유부터 하겠습니다. 어려운 개념이 아닙니다.

여러분이 팀장이라고 해봅시다. 조사할 게 산더미인데 혼자 다 읽으면 머리가 터집니다. 그래서 팀원 다섯에게 나눠 맡기고, 각자 요약 한 장씩 받습니다. 팀원들이 읽은 수백 페이지는 여러분 책상에 오지 않고, 결론만 옵니다.

서브에이전트가 정확히 이것입니다. 메인 AI(팀장)가 별도의 AI 인스턴스(팀원)에게 일을 맡기고, 그 팀원이 파일을 읽고 코드를 돌리고 계산한 뒤 요약만 돌려줍니다.

핵심 한 줄

서브에이전트의 가장 큰 값은 "빨라서"가 아니라 "메인 AI의 기억 공간을 안 쓰고 일을 끝내주기 때문"입니다. 이걸 컨텍스트 격리라고 부릅니다.

이 문서가 다루는 실제 사례

YouTube 영상 데이터를 분석하는 웹 대시보드 프로젝트입니다. 영상 260편의 썸네일(미리보기 이미지) 정보와 조회수·좋아요·업로드 시간 같은 기본 데이터가 CSV 파일에 들어 있고, 코드는 자바스크립트 파일 수십 개로 이뤄져 있습니다.

할 일은 두 가지였습니다. (1) 화면에 나오는 경고들이 다운로드 리포트에도 제대로 실리는지 점검하고, (2) 데이터를 파헤쳐 앱에 추가할 만한 아이디어를 뽑는 것.

혼자 하기엔 읽을 파일이 너무 많았습니다. 그래서 나눴습니다.

02왜 나눠야 하나 — 컨텍스트라는 그릇

AI에게는 "한 번에 기억할 수 있는 양"이 정해져 있습니다.

AI가 대화 중에 기억할 수 있는 분량을 컨텍스트 윈도우라고 합니다. 그릇이라고 생각하세요. 파일을 읽을 때마다 그릇에 물이 찹니다. 그릇이 넘치면 앞의 내용을 잊어버립니다.

이번 조사에서 에이전트들이 실제로 읽고 계산한 양은 토큰 약 113만이었습니다. 토큰은 AI가 글을 세는 단위인데, 한국어는 대략 한 글자에 1~1.5토큰이라고 보면 됩니다. 113만 토큰이면 책 여러 권 분량입니다.

이걸 메인 AI가 혼자 읽었다면 그릇이 진작에 넘쳐서 대화 자체가 불가능했을 겁니다. 그런데 나눠 맡기면 이렇게 됩니다.

그래서 언제 쓰나

읽어야 할 파일이 많고 결론만 필요할 때입니다. 반대로 "이 파일 3줄만 고쳐줘" 같은 일에 에이전트를 부르는 건 낭비입니다 — 팀원에게 시키고 보고받느니 직접 하는 게 빠릅니다.

03실제로 이렇게 굴렸습니다 — 3단계 11개

한꺼번에 11개를 부른 게 아닙니다. 단계마다 목적이 달랐습니다.

단계마다 설계가 달랐던 점

단계나눈 기준왜 그렇게 나눴나
1단계 점검파일 묶음별같은 파일을 두 명이 읽으면 중복 보고가 나온다. 파일 목록을 아예 겹치지 않게 잘랐다.
2단계 분석데이터 축별축이 다르면 관심 컬럼이 다르다. 한 명이 5개 축을 보면 축당 예산이 1/5로 준다.
3단계 검증역할별여기만 같은 자료를 준다. 대신 묻는 질문을 다르게 해서 세 각도로 보게 했다.

3단계가 앞의 둘과 다르다는 점이 중요합니다. 1·2단계는 일을 쪼갠 것이고, 3단계는 같은 결과물을 여러 각도로 검사한 것입니다. 목적이 다르면 나누는 방식도 달라야 합니다.

04브리프 실물 — 뭐라고 써서 보냈나

에이전트에게 주는 지시문을 브리프라고 부르겠습니다. 여기서 결과의 절반이 결정됩니다.

실제로 보낸 브리프의 뼈대입니다. 다섯 덩어리로 되어 있습니다.

[1] 작업 폴더와 안전장치
    절대 파일을 수정하지 마세요. git 명령도 실행하지 마세요.
    스크립트는 임시 폴더에만 쓰세요.

[2] 데이터와 환경
    sample_data/...csv (260행, 73컬럼, UTF-8 BOM)
    pandas 2.2.3 · scipy 1.15.3 사용 가능

[3] 당신의 축 — 다른 사람 것은 건드리지 마세요
    당신은 "제목 × 썸네일 문구"만 봅니다.
    다른 에이전트 4명이 채널/타이밍/반응/색 축을 맡습니다.

[4] 이미 있는 것 (또 제안하지 말 것)
    thumbnail-cross.js 에 겹침률 패널이 이미 있습니다.
    thumbnail.js 의 텍스트/문구 화면에 글자수 비교가 있습니다.

[5] 지켜야 할 규칙과 보고 형식
    표본 게이트: n>=30 신뢰 / 10~29 참고 / 10 미만 제외
    상관을 인과로 쓰지 말 것
    발견마다 수치와 n을 붙일 것. 추측은 "추측"이라고 명시할 것
    안 되는 것으로 판명난 것도 이유와 함께 적을 것

각 덩어리가 왜 필요한가

  • [1] 안전장치 — 에이전트가 파일을 고치면 누가 뭘 바꿨는지 추적이 안 됩니다. 조사 단계에서는 읽기 전용이 원칙입니다.
  • [2] 환경 — 없는 라이브러리를 찾느라 시간을 버리지 않게 미리 알려줍니다.
  • [3] 범위 — 이걸 안 쓰면 다섯이 같은 걸 발견해서 돌아옵니다.
  • [4] 이미 있는 것 — 가장 자주 빠뜨리는 항목입니다. 이게 없으면 이미 구현된 기능을 "아이디어"라고 들고 옵니다.
  • [5] 규칙과 형식 — 특히 "안 되는 것도 이유와 함께 적으라"가 값집니다. 다음 사람이 같은 시도를 반복하지 않게 됩니다.
효과가 컸던 한 줄

"추측은 '추측'이라고 명시하세요." 이 한 줄 때문에 에이전트들이 확인한 것과 짐작한 것을 구분해서 보고했고, 덕분에 어디를 다시 검산해야 할지 바로 알 수 있었습니다.

05실패 3장면

여기가 이 문서의 핵심입니다. 잘된 이야기보다 이쪽이 훨씬 쓸모 있습니다.

실패 ①

틀린 전제 하나가 세 명에게 그대로 복제됐다

1단계 브리프에 저는 이렇게 썼습니다.

"썸네일 화면 8개가 전부 excludeFromReport 플래그를 달고 있어서 리포트에 안 들어갑니다. 이건 이미 확인된 사실이니 다시 확인할 필요 없습니다."

이게 틀렸습니다. 코드에는 정반대의 주석이 있었습니다.

// 이 플래그는 여기서 일부러 무시한다 —
// "전체본에 넣지 않는다"는 뜻이지 "어떤 리포트에도 못 넣는다"가 아니다.

실제로는 썸네일 전용 리포트가 화면 7개를 통째로 담고 있었습니다. 그런데 저는 이 틀린 전제를 세 개 브리프에 모두 복사해서 보냈습니다.

다행히 두 번째 에이전트가 코드를 읽는 대신 실제로 브라우저를 띄워 리포트를 발행해봤고, 거기서 전제가 깨졌습니다. 만약 셋 다 코드만 읽었다면 셋 다 사이좋게 같은 결론을 냈을 것이고, 저는 그걸 "세 명이 독립적으로 확인했다"고 읽었을 겁니다.

배운 것 — 에이전트를 여러 개 돌린다고 독립 검증이 되지 않습니다. 같은 브리프를 받으면 같은 편향을 공유합니다. 브리프에는 내 결론을 넣지 말고 "확인하고 오라"고 시켜야 합니다.

실패 ②

이미 구현된 기능을 두 명이 "발견"했다

2단계에서 서로 다른 축을 맡은 에이전트 둘이 같은 것을 보고했습니다.

"저해상도 판별 플래그가 고장 났습니다. 640×480짜리 5건이 전부 '정상'으로 표시돼 있습니다."

데이터상으로는 맞는 말이었습니다. 저는 이걸 "축이 다른 두 명이 독립적으로 같은 버그를 찾았다"며 좋은 신호로 보고했습니다.

그런데 나중에 코드를 직접 확인해보니, 앱이 이미 그 불일치를 화면에 띄우고 있었습니다.

// thumbnail.js — 이미 있던 코드
const smallButNotFlagged = all.filter(row =>
  가로해상도 < 1280 && 저해상도플래그 === 'N');
// → "저해상도 플래그 불일치" 라는 항목으로 화면에 표시 중

두 에이전트는 CSV 데이터만 봤고 앱 코드는 안 봤습니다. 제가 그들에게 준 축이 "데이터 분석"이었으니 당연한 결과였습니다. 문제는 제가 코드 확인 없이 그대로 "발견"으로 전달한 것입니다.

배운 것 — 에이전트의 범위를 자르면 그 밖은 못 봅니다. 데이터 담당은 코드를 모르고, 코드 담당은 데이터를 모릅니다. 종합하는 사람(메인)이 경계를 넘는 확인을 해야 합니다.

실패 ③

같은 데이터인데 두 명의 결론이 정반대였다

3단계 데이터 검증자가 2단계 분석자의 주장을 반박했습니다.

주장
분석자"언어를 나눠서 보면 효과가 사라집니다. 한글만 보면 p=0.606"
검증자"재현 안 됩니다. 한글만 봐도 효과가 남습니다. p=0.046"

둘 중 하나가 틀린 게 아니라 둘 다 맞았습니다. 제가 직접 양쪽 방식으로 다시 계산해보니 이렇게 나왔습니다.

어떤 지표로 쟀나전체한글만비한글만
일평균 조회수로 재면p=0.026p=0.606 (사라짐)p=0.221
누적 조회수로 재면p=0.023p=0.046 (남음)p=1.000

분석자는 일평균으로, 검증자는 누적으로 쟀던 것입니다. 브리프 어디에도 "어느 지표로 재라"는 말이 없었기 때문입니다.

배운 것 — 결론이 갈리면 먼저 계산 조건이 같았는지 확인하세요. 그리고 브리프에 측정 방법을 못박아야 이런 일이 안 생깁니다. 참고로 이 충돌은 버그가 아니라 발견이었습니다 — "지표를 바꾸면 결론이 뒤집힌다"는 사실 자체가 화면에 표시해야 할 정보였습니다.

06성공 장면 — 진짜 독립 검증은 이렇게 생겼다

실패 ①과 대비해서 보면 차이가 선명합니다.

성공

세 검증자가 서로 다른 이유로 같은 항목을 막았다

분석자들이 낸 아이디어 중 "글자 없는 썸네일 = 호감형 카드를 만들자"는 항목이 있었습니다. 통계적으로는 꽤 강해 보였습니다.

세 검증자가 각자 다른 근거로 이걸 막았습니다.

  • 데이터 검증자 — "효과 자체는 견고합니다. 다만 서로 다른 세 정의를 하나로 묶어서 표본을 만들었는데, 그 세 정의는 원래 27건만 일치합니다."
  • 구현 검증자 — "이 지표는 기존 코드에 이미 있는 축과 방향이 반대입니다. 두 화면이 같은 것을 반대로 읽게 됩니다."
  • 제품 검증자 — "이름 자체가 처방입니다. '호감형'은 댓글이 적어도 점수가 오르는 지표인데, 그러면 무반응을 미덕으로 번역하게 됩니다."

왜 이건 진짜 검증인가 — 셋에게 준 자료는 같았지만 질문이 달랐습니다. 그래서 각자 다른 곳을 봤고, 서로 다른 이유로 같은 결론에 닿았습니다. 실패 ①은 같은 질문을 세 명에게 줬기 때문에 같은 답이 나온 것이고, 이건 다른 질문인데도 같은 답이 나온 것입니다. 이 차이가 전부입니다.

기억할 공식

같은 자료 + 같은 질문 = 답이 같아도 증거가 아님 (편향 복제)
같은 자료 + 다른 질문 = 답이 같으면 강한 증거
다른 자료 + 다른 질문 = 가장 강함 (그림 2의 2단계에서 축이 다른 두 명이 같은 결함을 지목한 경우)

07숫자로 본 비용

공짜가 아닙니다. 얼마나 들었는지 그대로 적습니다.

11개에이전트 (3+5+3)
1.13M소비 토큰
198회도구 호출
32건최종 아이디어

이 비용이 아깝지 않았던 이유

  • 혼자서는 불가능했습니다. 113만 토큰은 대화 하나에 다 담을 수 없는 양입니다.
  • 깊이가 달랐습니다. 한 축에 8만 토큰을 쓴 덕분에 검정 40개를 돌리고 다중비교 보정까지 했습니다. 혼자 5개 축을 봤다면 축당 예산이 1/5로 줄어 표면만 훑었을 겁니다.
  • 제 오류가 세 번 잡혔습니다. 실패 ①·③과, 제가 옛 버전 파일을 읽고 있다는 지적까지.
반대로 아까웠던 지점

결과가 요약으로만 오기 때문에 중간 과정을 볼 수 없습니다. 틀렸는지 확인하려면 결국 메인이 검산해야 하고, 실제로 이번에도 주요 수치는 전부 다시 계산했습니다. 검산 비용을 미리 예산에 넣으세요.

08체크리스트

여기만 떼어 다른 프로젝트에 써도 됩니다.

이럴 때 서브에이전트를 쓰세요

  • 읽을 파일이 많고 결론만 필요할 때파일 내용이 아니라 판단만 있으면 되는 경우. 컨텍스트 격리의 값이 가장 큽니다.
  • 독립적인 일을 동시에 여러 개 돌릴 때서로 결과를 기다리지 않아도 되는 작업들. 축·파일·주제로 자를 수 있어야 합니다.
  • 한 주제를 깊게 파야 할 때축당 예산을 온전히 줄 수 있습니다. 혼자 여러 축을 보면 전부 얕아집니다.
  • 같은 결과물을 여러 각도로 검사할 때단, 반드시 질문을 다르게 줘야 합니다. 같은 질문이면 검증이 아닙니다.

이럴 땐 쓰지 마세요

  • 어디를 고칠지 이미 아는 작은 수정파일과 줄 번호를 아는 일은 직접 하는 게 빠릅니다. 보고받는 시간이 더 듭니다.
  • 축이 서로 얽혀 있어서 경계를 넘는 게 핵심일 때다섯으로 자르면 "언어 × 채널 × 시대"가 얽힌 문제는 아무도 못 봅니다.
  • "여러 명이 같은 답을 내면 맞겠지"를 기대할 때실패 ①이 정확히 이 함정입니다. 같은 브리프 = 같은 편향입니다.
  • 사실 확인 한 건파일 하나 grep 한 번이면 끝나는 일에 에이전트를 부르지 마세요.

브리프 작성 규칙 7가지

#규칙안 지키면
1내 결론을 전제로 주지 말 것. "확인하고 오라"고 시킬 것실패 ① — 틀린 전제가 전원에게 복제됨
2"이미 있는 것"을 명시할 것구현된 기능을 아이디어로 들고 옴
3범위를 겹치지 않게 자를 것. 남의 영역을 명시적으로 금지중복 보고, 예산 낭비
4측정 방법을 못박을 것 (어느 지표, 어느 기준)실패 ③ — 결론이 갈리고 원인 추적에 시간이 듦
5읽기 전용을 기본으로. 파일 수정·git 금지누가 뭘 바꿨는지 추적 불가
6"추측은 추측이라고 쓰라"고 요구할 것확인한 것과 짐작한 것이 뒤섞임
7"안 되는 것도 이유와 함께" 적게 할 것다음 사람이 같은 시도를 반복함

결과를 받은 뒤 메인이 해야 할 일

  • 중요한 판정은 직접 검산하세요. 이번에는 "높음" 등급 주장을 전부 다시 계산했고, 그 과정에서 두 건을 정정했습니다.
  • 경계를 넘는 확인을 하세요. 데이터 담당이 "버그다"라고 하면, 코드가 이미 처리하고 있는지 확인하는 건 메인의 몫입니다 (실패 ②).
  • 결론이 갈리면 조건부터 맞춰보세요. 대개 계산 방법이 달랐던 것입니다 (실패 ③).
  • 보고서를 그대로 믿지 마세요. 에이전트도 틀립니다. 다만 여러분도 틀립니다 — 이번에는 에이전트가 저를 세 번 잡아냈습니다.

09용어 정리

용어뜻
서브에이전트메인 AI가 일을 맡기는 별도의 AI 인스턴스. 자기 작업 공간에서 일하고 요약만 돌려준다.
컨텍스트 윈도우AI가 한 번에 기억할 수 있는 분량. 그릇의 크기.
컨텍스트 격리에이전트가 읽은 내용이 메인의 그릇에 들어오지 않는 것. 서브에이전트의 핵심 이점.
토큰AI가 글을 세는 단위. 한국어는 대략 한 글자에 1~1.5토큰.
브리프에이전트에게 주는 지시문. 범위·규칙·보고 형식을 담는다.
파이프라인앞 단계의 결과를 뒤 단계가 받아 처리하는 구조. 이번엔 점검 → 분석 → 검증.
편향 복제같은 브리프를 받은 에이전트들이 같은 실수를 공유하는 현상. 다수결이 안 통하는 이유.
