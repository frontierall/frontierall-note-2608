01한 줄 정의와 비유

어려운 개념이 아닙니다. 회사 조직에 빗대면 바로 이해됩니다.

한 줄 정의

서브 에이전트는 메인 AI(오케스트레이터)가 특정 작업을 맡기는, 독립된 작업 공간과 독립된 기억 공간을 가진 별도의 AI 인스턴스입니다.

팀장과 팀원을 떠올려 보세요. 팀장이 조사할 게 산더미인데 혼자 다 읽으면 감당이 안 됩니다. 그래서 팀원 몇 명에게 부분씩 나눠 맡기고, 각자 자기 자리에서 조사한 뒤 요약 보고서만 팀장 책상에 올립니다. 팀원이 읽은 자료 수백 페이지는 팀장 책상에 쌓이지 않습니다. 결론만 옵니다.

서브 에이전트가 정확히 이 구조입니다. 메인 에이전트(팀장)가 지시문(브리프)을 써서 서브 에이전트(팀원)에게 넘기면, 서브 에이전트는 자기만의 작업 공간에서 파일을 읽고, 코드를 돌리고, 웹을 검색하고, 계산을 마친 뒤 요약 결과만 메인에게 돌려줍니다.

02메인 에이전트와 서브 에이전트의 관계

서브 에이전트는 혼자 존재하지 않습니다. 항상 누군가 부르고, 누군가 결과를 받습니다.

  • 메인 에이전트(오케스트레이터) — 사용자와 직접 대화하는 쪽입니다. 무엇을 나눠야 할지 판단하고, 서브 에이전트에게 지시문(브리프)을 써서 보내고, 돌아온 요약들을 종합해 최종 답을 만듭니다.
  • 서브 에이전트 — 메인이 시킨 범위 안에서만 일합니다. 자기 작업 공간과 자기 기억 공간을 따로 갖고 있어서, 메인의 대화 내용을 함부로 침범하지 않습니다.

중요한 건 서브 에이전트는 사용자와 직접 대화하지 않는다는 점입니다. 결과는 항상 메인을 거쳐 사용자에게 전달됩니다. 그래서 서브 에이전트가 무엇을 하고 있는지는 보통 사용자에게 실시간으로 보이지 않고, 끝난 뒤 요약 보고로만 드러납니다.

호칭이 여러 개인 이유

도구마다 부르는 이름이 다를 뿐 구조는 같습니다. "서브 에이전트", "Task", "팀원 에이전트", "워커 에이전트" 모두 메인이 위임하고 요약만 받는다는 같은 패턴을 가리킵니다.

03왜 필요한가 — 컨텍스트 윈도우 문제

서브 에이전트를 쓰는 가장 큰 이유는 "빨라서"가 아닙니다.

AI가 한 번의 대화에서 기억할 수 있는 분량을 컨텍스트 윈도우라고 부릅니다. 그릇이라고 생각하면 됩니다. 파일을 읽고, 검색 결과를 받고, 대화를 주고받을 때마다 그릇에 내용이 찹니다. 그릇이 넘치면 앞의 내용을 잊어버리거나, 새 내용을 담을 자리가 없어집니다.

읽어야 할 파일이 수십 개, 검색해야 할 자료가 방대할 때 메인 에이전트가 그걸 전부 직접 읽으면 그릇이 금방 넘칩니다. 이때 서브 에이전트에게 나눠 맡기면, 각 서브 에이전트가 읽은 원본 내용은 메인의 그릇에 들어오지 않고 결론 요약만 들어옵니다. 이걸 컨텍스트 격리라고 부릅니다.

핵심 한 줄

서브 에이전트의 가장 큰 값은 "메인의 기억 공간을 쓰지 않고 일을 끝내주는 것"입니다. 그래서 대화가 길어져도 메인의 그릇에는 여유가 남습니다.

이 구조가 실제로 어떻게 작동했는지 궁금하다면, 아래 서브에이전트 11개 사례 연구에 113만 토큰이 요약 2만 자로 줄어드는 실제 수치가 나옵니다.

04서브 에이전트가 실제로 하는 일 3가지 패턴

이름은 하나지만 쓰임새는 세 갈래로 나뉩니다.

① 병렬 조사 — 넓게 나눠서 동시에

서로 독립적인 여러 조사를 동시에 돌립니다. 예: 파일 묶음별로 셋에게 나눠 코드베이스를 훑게 하기. 결과를 기다리는 시간이 겹치지 않아 전체 소요 시간이 줄어듭니다.

② 심화 분석 — 한 주제를 깊게

주제를 축(관점)별로 쪼개 각자 한 축만 깊게 파고들게 합니다. 한 명이 다섯 개 축을 다 보면 축당 예산이 1/5로 줄어 표면만 훑게 되지만, 다섯 명이 축 하나씩 맡으면 각자 깊이 들어갈 수 있습니다.

③ 교차 검증 — 같은 결과물을 다른 질문으로

이미 나온 결론을 서로 다른 기준(예: 데이터 관점 / 구현 관점 / 사용자 관점)으로 다시 점검하게 합니다. 같은 자료라도 질문이 다르면 독립적인 검증이 됩니다.

흔한 오해

"여러 서브 에이전트에게 같은 질문을 던져서 같은 답이 나오면 검증된 것이다" — 이건 틀렸습니다. 같은 브리프를 받으면 같은 편향을 그대로 복제해서 돌려줄 뿐입니다. 교차 검증이 되려면 질문 자체가 달라야 합니다. 실제 실패 사례는 서브에이전트 11개 사례 연구 · 실패 3장면에서 확인할 수 있습니다.

05서브 에이전트가 아닌 것

비슷해 보이지만 다른 개념들과 구분해 두면 헷갈리지 않습니다.

비교 대상차이
단순 함수 호출 / Tool Calling도구 호출은 정해진 입출력 형식으로 즉시 값을 돌려주는 단발성 호출입니다. 서브 에이전트는 스스로 판단하며 여러 단계를 거쳐 일을 수행하는 또 다른 AI라는 점이 다릅니다.
RAG의 검색 단계RAG는 문서를 찾아 컨텍스트에 넣는 검색 과정입니다. 서브 에이전트는 검색을 포함해 더 넓은 임의의 작업(코드 실행, 계산, 브라우저 조작 등)을 맡을 수 있습니다.
멀티 에이전트 시스템여러 에이전트가 협업하는 큰 틀을 말합니다. 서브 에이전트 위임은 그 안에서 메인이 중심을 잡는 한 가지 구현 방식(오케스트레이터-워커 패턴)입니다.

06언제 쓰고 언제 쓰지 말아야 하나

가장 실전적인 판단 기준만 추립니다. 자세한 체크리스트와 브리프 작성 규칙은 사례 연구 문서에 있습니다.

이럴 때 쓰세요

  • 읽을 자료가 많고 결론만 필요할 때원본 내용이 아니라 판단 결과만 있으면 되는 경우.
  • 독립적인 작업을 동시에 여러 개 처리할 때서로 결과를 기다리지 않아도 되는 작업들.
  • 결과물을 여러 각도로 검증할 때단, 질문을 반드시 다르게 줘야 진짜 검증이 됩니다.

이럴 땐 쓰지 마세요

  • 어디를 고칠지 이미 아는 작은 수정지시하고 보고받는 시간이 직접 하는 것보다 더 듭니다.
  • 사실 확인 한 건파일 하나 확인하면 끝나는 일에 별도 인스턴스를 부르는 건 낭비입니다.
  • 결과를 실시간으로 지켜봐야 할 때서브 에이전트는 끝나야 요약을 돌려줍니다. 중간 과정을 계속 확인해야 하는 일에는 맞지 않습니다.

07용어 정리

용어뜻
서브 에이전트메인 에이전트가 일을 맡기는 별도의 AI 인스턴스. 자기 작업 공간에서 일하고 요약만 돌려준다.
메인 에이전트 / 오케스트레이터사용자와 직접 대화하며 무엇을 나눌지 판단하고, 서브 에이전트들의 결과를 종합하는 쪽.
브리프서브 에이전트에게 주는 지시문. 범위·규칙·보고 형식을 담는다.
컨텍스트 윈도우AI가 한 번에 기억할 수 있는 분량. 그릇의 크기.
컨텍스트 격리서브 에이전트가 읽은 원본 내용이 메인의 그릇에 들어오지 않는 것. 서브 에이전트의 핵심 이점.
병렬 실행여러 서브 에이전트를 동시에 돌려 서로의 결과를 기다리지 않게 하는 방식.
편향 복제같은 브리프를 받은 서브 에이전트들이 같은 실수를 그대로 반복하는 현상. 다수결이 검증이 되지 않는 이유.
한 문장으로 요약하면

서브 에이전트는 메인 에이전트의 기억 공간을 아끼면서 일을 나눠 처리하게 해주는 AI 인스턴스입니다. 도구 호출보다 넓은 일을 맡을 수 있고, 대신 결과는 요약으로만 돌아오기 때문에 중요한 판단은 메인이 직접 다시 확인해야 합니다.
