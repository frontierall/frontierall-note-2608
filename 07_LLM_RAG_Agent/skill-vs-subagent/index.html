01헷갈리는 이유 — 둘 다 .md 파일이라서

겉모습이 비슷해서 처음엔 뭐가 다른지 감이 잘 안 옵니다.

둘 다 frontmatter가 있는 마크다운 파일이고, 둘 다 "이런 요청이 오면 이렇게 처리하라"는 규칙을 적어둡니다. name과 description을 쓴다는 것도 같습니다. 그래서 "그냥 아무거나 쓰면 되는 거 아니야?"라는 생각이 들기 쉬운데, 실제로 실행되는 방식이 완전히 다릅니다.

이 문서를 읽기 전에 스킬이란 무엇인가?와 서브 에이전트란 무엇인가?를 먼저 보고 오면 이해가 훨씬 빠릅니다. 여기서는 둘을 나란히 놓고 "그래서 실제로 뭘 골라야 하는지"만 다룹니다.

02결정적 차이 한 가지 — 컨텍스트가 어디에 쌓이는가

다른 차이는 전부 이 하나에서 파생됩니다.

이것만 기억하면 됩니다

스킬은 지금 이 대화 자신이 절차를 읽고 실행합니다 — 그 과정에서 읽은 파일, 검색 결과가 전부 지금 대화의 기억 공간에 그대로 쌓입니다.

서브 에이전트는 별도의 AI 인스턴스가 자기만의 기억 공간에서 일하고, 결과 요약만 지금 대화로 돌아옵니다. 읽은 원본은 돌아오지 않습니다.

이 차이 하나에서 나머지 특징들이 전부 갈라집니다 — 얼마나 많은 걸 처리할 수 있는지, 안전 장치를 어떻게 거는지, 병렬로 여러 개를 돌릴 수 있는지까지 전부요.

03비교표

스킬서브 에이전트
실행 주체지금 대화 중인 AI 자신별도로 새로 뜨는 AI 인스턴스
기억 공간메인 대화와 공유 (격리 없음)독립적 (컨텍스트 격리)
많은 자료를 읽어야 할 때메인의 그릇이 그대로 참 — 대화가 길어지면 부담원본은 서브 에이전트 안에서 소비, 메인은 요약만 받음
도구 제한제한 항목 없음 — 메인이 가진 도구를 그대로 씀tools 목록으로 명시적 제한 가능 (예: 읽기 전용)
병렬 실행스킬 자체는 하나의 절차를 순차 진행여러 개를 동시에 띄워 병렬 처리 가능
호출 방식/이름 직접 호출, 또는 요청과 description이 맞으면 자동메인(또는 스킬)이 필요할 때 명시적으로 호출
적합한 일순서·규칙을 저장해두고 싶은 절차컨텍스트를 많이 먹는 조사·분석·검증 작업

04결정 트리 — 세 가지 질문

순서대로 물어보면 대부분 답이 나옵니다.

  1. 이 일이 파일을 많이 읽거나, 웹을 많이 검색하거나, 결과가 길게 나올 것 같은가?
    그렇다 → 서브 에이전트로. 메인의 기억 공간을 지키기 위해서입니다.
    아니다 → 다음 질문으로.
  2. "이 작업은 특정 도구만 쓰게 하고 싶다" 같은 제한이 필요한가? (예: 절대 파일을 고치면 안 된다)
    그렇다 → 서브 에이전트로. tools 목록으로 못박을 수 있습니다.
    아니다 → 다음 질문으로.
  3. 여러 단계·조건 분기가 있는 절차를 반복해서 쓰고 싶은가?
    그렇다 → 스킬로. 순서와 규칙을 한 번 적어두고 재사용합니다.
    아니다 → 굳이 둘 다 필요 없을 수 있습니다. 그냥 한 번 물어보는 게 더 빠를 수 있습니다.
참고 — 둘 다 필요하다면

1번과 2번은 "예", 3번도 "예"라면 — 즉 여러 단계 절차인데, 그중 특정 단계가 컨텍스트를 많이 먹거나 도구 제한이 필요하다면 — 08장에서 다루는 것처럼 스킬이 서브 에이전트를 호출하는 조합을 씁니다. 흔한 패턴입니다.

05잘못 골랐을 때 생기는 일

두 가상 시나리오로 감을 잡아보겠습니다.

스킬로만 처리했을 때 (컨텍스트를 많이 쓰는 일)

"프로젝트 전체 코드를 스킬 하나로 훑어서 요약하기"

스킬은 메인 대화 자신이 실행하므로, 파일 수십 개를 읽는 동안 그 내용이 전부 메인의 기억 공간에 쌓입니다. 대화가 길어질수록 그릇이 꽉 차서, 정작 이후 대화에서 앞부분을 잊어버리는 일이 생길 수 있습니다.

이럴 땐 서브 에이전트가 맞습니다. 원본은 서브 에이전트 안에서 소비되고, 메인은 요약만 받으면 됩니다.

서브 에이전트로만 처리했을 때 (간단한 반복 규칙)

"커밋 메시지 형식을 매번 서브 에이전트에게 맡기기"

커밋 메시지 형식을 맞추는 건 파일을 많이 읽을 필요도, 격리할 이유도 없는 간단한 규칙입니다. 그런데도 매번 별도 인스턴스를 띄우면, 결과가 요약으로만 돌아와서 오히려 세부 조정이 번거로워지고, 호출하는 시간만 더 듭니다.

이럴 땐 스킬이 맞습니다. 규칙을 한 번 적어두면 메인이 직접, 빠르게 처리합니다.

06실전 조합 — 스킬이 서브 에이전트를 부르는 구조

둘은 경쟁 관계가 아니라, 자주 함께 쓰입니다.

문서 최신화·팩트체크 에이전트 만들기에서 만든 doc-refresh 스킬이 이 조합의 실제 예입니다.

  • 스킬(doc-refresh)이 맡는 것 — "몇 단계로, 어떤 순서로 진행할지", "사람 승인을 반드시 거칠 것" 같은 절차와 규칙. 이건 반복해서 재사용할 규칙이라 스킬이 맞습니다.
  • 서브 에이전트(doc-researcher/doc-fact-checker/doc-writer)가 맡는 것 — 웹 검색·재검증처럼 컨텍스트를 많이 먹는 실제 조사·분석 작업. 그리고 "이 단계는 절대 파일을 고치면 안 된다"는 제한을 tools로 강제할 수 있어야 하는 작업.

정리하면, "무엇을 언제 할지"는 스킬이 기억하고, "그중 무거운 작업 하나하나"는 서브 에이전트가 처리합니다. 스킬 혼자서는 컨텍스트가 넘치고, 서브 에이전트만 여럿 있어도 누가 언제 부를지 정하는 사람이 없으면 무용지물입니다.

07체크리스트

  • 절차·규칙을 재사용하고 싶다 → 스킬"이 요청이 오면 이 순서로" 같은 반복 패턴.
  • 컨텍스트를 많이 먹는 조사·분석이 필요하다 → 서브 에이전트메인의 기억 공간을 지키기 위해 격리.
  • 도구를 명시적으로 제한하고 싶다 → 서브 에이전트tools 목록이 곧 안전장치.
  • 여러 단계 절차 안에 무거운 작업이 섞여 있다 → 스킬 + 서브 에이전트 조합doc-refresh가 이 패턴의 예.
  • 딱 한 번뿐인 요청스킬도 서브 에이전트도 필요 없습니다. 그냥 채팅으로 물어보세요.

08용어 정리 & 다음 단계

용어뜻
컨텍스트 격리서브 에이전트가 읽은 내용이 메인의 기억 공간에 들어오지 않는 것. 스킬에는 없는 특성.
오케스트레이터-워커 패턴스킬(또는 메인)이 절차를 정하고, 서브 에이전트들이 각자 맡은 일을 처리하는 조합 구조.
tools 제한서브 에이전트 정의 파일의 tools 항목으로 쓸 수 있는 도구를 명시적으로 좁히는 것. 스킬에는 대응 개념이 없음.
한 문장으로 요약하면

순서와 규칙은 스킬에, 컨텍스트가 많이 드는 실제 작업은 서브 에이전트에. 둘 다 필요 없다면 그냥 채팅으로 물어보는 게 가장 빠릅니다.
