01왜 이런 에이전트가 필요한가

AI가 쓴 문서든 사람이 쓴 문서든, 시간이 지나면 낡습니다.

가격, 버전, 정책, API 스펙, 링크 — 문서에 적힌 이런 내용은 시간이 지나면 틀린 정보가 됩니다. 게다가 LLM에게 "이거 최신 정보로 고쳐줘"라고 그냥 시키면, 두 가지 문제가 생깁니다.

  • 모델이 자기 학습 데이터로 답한다. 학습 시점 이후 바뀐 내용은 알 수가 없는데도, 마치 아는 것처럼 자신 있게 틀린 답을 씁니다.
  • 검색을 하더라도, 검색 결과 하나를 그대로 믿는다. 첫 번째로 나온 블로그 글이 틀렸거나 오래됐어도 그걸 그대로 옮겨 적습니다.

이 문서에서 만드는 에이전트는 이 두 문제를 구조로 막습니다. "조사하는 사람"과 "그 조사가 맞는지 다시 확인하는 사람"을 분리하고, 사람이 승인하기 전에는 파일을 건드리지 않게 만드는 것이 핵심입니다.

이 교안에서 실제로 만드는 것

문서/대본을 읽고 → 웹 검색으로 최신 정보와 대조하고 → 근거(출처)와 확신도를 붙여 변경을 제안하고 → 사람이 승인한 것만 실제로 반영하는 에이전트 파이프라인입니다. 아래 예시 코드는 실제로 이 강의 자료 저장소에 적용한 것을 그대로 가져왔습니다.

02설계 원칙 — 왜 역할을 3개로 쪼개나

에이전트 하나가 검색부터 수정까지 한 번에 하면, 실수가 그대로 파일에 들어갑니다.

원칙 1 — 조사와 검증은 반드시 다른 질문이어야 한다

서브에이전트 11개 사례 연구에서 다룬 함정이 정확히 여기서 재발합니다. 검증 담당에게 "이 리서처가 맞다고 했는데, 맞아?"라고 물으면 같은 출처를 보고 같은 답을 하기 쉽습니다. 그래서 검증 담당에게는 "이 사실을 원출처에서 처음부터 다시 확인해봐"라고 시켜야 합니다. 질문 자체가 다르면, 같은 실수를 그대로 반복할 확률이 줄어듭니다.

원칙 2 — 조사·검증 단계는 파일을 건드릴 수 없어야 한다

리서처와 팩트체커에게는 아예 Write/Edit 도구를 주지 않습니다. 결과가 "제안 목록"으로만 나오게 강제하는 것입니다. 이러면 중간에 판단이 틀려도 파일에는 아직 아무 영향이 없습니다.

원칙 3 — 검증을 통과한 것만, 그리고 사람이 승인한 것만 반영한다

팩트체커가 "확인됨(CONFIRMED)"이라고 판정한 항목만 작성 단계로 넘깁니다. 그리고 작성 단계가 만든 초안(diff)도 곧바로 파일에 쓰지 않고, 사람에게 먼저 보여주고 승인을 받은 뒤에만 실제로 수정합니다.

한 줄로 요약하면

조사(Research) → 독립 검증(Verify) → 초안 작성(Draft) → 사람 승인 → 반영(Apply). 이 5단계 중 앞 세 단계는 전부 되돌릴 수 있는 "제안"일 뿐이고, 실제로 파일이 바뀌는 건 마지막 단계뿐입니다.

03전체 구조 한눈에 보기

에이전트 3개 + 이들을 부르는 스킬 1개, 총 4개 파일로 이뤄집니다.

041단계 — 서브 에이전트 3개 만들기

서브 에이전트는 frontmatter가 있는 마크다운 파일 한 장입니다. 코드가 아닙니다.

서브 에이전트 정의 파일은 이름.md 하나로 끝납니다. 맨 위에 이런 형식의 frontmatter를 씁니다.

---
name: doc-researcher
description: 언제 이 에이전트를 써야 하는지 한 문단으로. 오케스트레이터가
             이 설명만 보고 호출 여부를 판단하므로 구체적으로 쓸수록 좋다.
tools: Read, Grep, Glob, WebSearch, WebFetch
model: sonnet
permissionMode: default
---

# 본문에는 이 에이전트가 지켜야 할 규칙을 자연어로 적는다.
# "무엇을 받고, 무엇을 하고, 무엇을 돌려주는가"를 명확히.
  • name — 다른 에이전트/스킬에서 이 이름으로 호출한다.
  • description — 언제 써야 하는지. 이 설명이 부실하면 필요할 때 안 불려오거나, 엉뚱할 때 불려온다.
  • tools — 이 목록이 안전장치의 핵심이다. 조사·검증 담당에게는 Write/Edit을 아예 주지 않는다.

doc-researcher — 읽기 전용 조사자

문서를 읽고, 검색으로 최신 정보와 대조해서, 근거와 확신도가 붙은 변경 제안 목록만 돌려줍니다. 실제 정의 파일의 핵심 부분입니다.

tools: Read, Grep, Glob, WebSearch, WebFetch   # Write/Edit 없음

## 무엇을 만드는가 (발췌)
각 항목마다:
- 위치 — 문서 어디인지
- 현재 내용 / 제안 변경
- 근거 — 출처 URL과 그 출처가 뒷받침하는 구체적 사실
- 확신도 — 확인됨 / 추정 / 불확실

## 지켜야 할 규칙
- 학습 데이터로 "이미 안다"고 판단하지 말고, 시간에 민감한 내용은
  전부 실제로 검색해서 재확인한다.
- 근거 없는 주장("최신이 아닌 것 같다")은 항목으로 인정하지 않는다.

doc-fact-checker — 독립적으로 다시 확인하는 검증자

여기가 이 설계의 핵심입니다. 리서처가 낸 근거를 그냥 다시 열어보고 끄덕이는 게 아니라, 원출처를 처음부터 다시 찾아 스스로 다시 도출합니다.

tools: Read, Grep, Glob, WebSearch, WebFetch   # 여기도 Write/Edit 없음

## 무엇을 다르게 하는가
1. 인용된 URL을 열어보되, 리서처의 요약을 보기 전에 원문에서
   직접 사실을 다시 뽑아본다.
2. 그 출처가 이 주장에 권위 있는 출처인지 따진다
   (공식 문서/체인지로그 > 뉴스 > 블로그 > 포럼).
3. 그 출처보다 더 최신 자료가 있는지 한 번 더 찾아본다.

## 판정
CONFIRMED / INCORRECT / UNCERTAIN 중 하나 + 근거.
"리서처가 틀렸다"고 말하는 걸 주저하지 않는다 — 그게 이 단계의 존재 이유다.

doc-writer — 톤을 맞춰 초안만 쓰는 작성자

tools: Read, Grep, Glob   # 검색도, 쓰기도 없음 — 이미 확인된 사실만 문장으로

## 무엇을 받는가
CONFIRMED 판정을 받은 항목만. UNCERTAIN/INCORRECT는 애초에 넘어오지 않는다.

## 무엇을 만드는가
항목마다 위치 / 기존 문장 / 새 문장 을 문서의 기존 문체·형식에 맞춰 작성.
문서를 훑다가 확인 목록에 없는 다른 문제를 발견해도 고치지 않고
"별도 제안"으로만 남긴다 — 검증 안 된 내용이 슬쩍 끼어드는 걸 막기 위해.
자주 하는 실수

세 역할을 한 에이전트에 다 몰아넣고 "검색하고, 확인하고, 고쳐줘"라고 시키는 것. 이러면 원칙 1·2가 전부 무너집니다 — 검색한 사람과 확인한 사람이 같은 존재가 돼버리고, 확인이 끝나기도 전에 파일을 고칠 도구를 이미 쥐고 있게 됩니다.

052단계 — 오케스트레이션 스킬 만들기

스킬은 "이 셋을 어떤 순서로, 무엇을 주고받으며 부를지"를 정하는 대본입니다.

스킬 파일은 스킬이름/SKILL.md 경로에 둡니다. frontmatter는 name과 description만 있으면 됩니다 — 나머지 본문이 곧 실행 절차입니다.

---
name: doc-refresh
description: 문서/스크립트를 웹 리서치로 최신화하고, 모든 제안을
             원출처에서 독립적으로 재검증한 뒤 초안을 작성한다 —
             파일이 실제로 바뀌기 전에. "이 문서 최신화해줘",
             "팩트체크 해줘" 같은 요청에 사용.
---

## 절차
1. 대상 문서와 점검 범위를 확인한다.
2. doc-researcher를 불러 제안 목록(근거·확신도 포함)을 받는다.
3. doc-fact-checker에게 원문서 + 그 제안 목록을 통째로 넘겨
   독립적으로 재검증하게 한다.
4. CONFIRMED만 골라 doc-writer에게 넘겨 초안(diff)을 받는다.
5. 초안 + 출처 + (INCORRECT/UNCERTAIN 항목)을 사람에게 보여주고
   승인을 받는다. 승인 전에는 Edit을 호출하지 않는다.
6. 승인 후 실제로 파일을 고치고, 무엇을 반영/보류했는지 보고한다.
스킬과 서브 에이전트의 역할 차이

서브 에이전트 3개는 각자 좁은 규칙만 압니다("나는 검증만 한다"). 전체 순서와 승인 게이트를 아는 건 스킬뿐입니다. 이 분리 덕분에 나중에 "리서처를 두 개로 나눠 병렬로 돌리자" 같은 절차 변경을 스킬 한 파일만 고쳐서 반영할 수 있습니다.

06저장 위치 정하기 — 이 프로젝트, 아니면 여러 프로젝트

파일을 어디에 두느냐가 곧 "누가 이 에이전트를 쓸 수 있는가"를 정합니다.

저장 위치적용 범위이런 경우에
<프로젝트>/.claude/agents/, .claude/skills/그 프로젝트만이 강의 자료처럼 한 저장소에서만 쓸 때
~/.claude/agents/, ~/.claude/skills/이 컴퓨터의 모든 프로젝트대부분의 저장소가 비슷한 성격일 때
별도 공유 저장소 + 심볼릭 링크연결한 프로젝트만이 컴퓨터에 성격이 다른 프로젝트도 섞여 있을 때

이 강의 자료 시리즈처럼 비슷한 성격의 저장소 몇 개가 같은 에이전트를 쓰고 싶은데, 같은 컴퓨터에 무관한 프로젝트도 섞여 있다면 세 번째 방식이 맞습니다. 실체 파일은 홈 폴더의 별도 저장소(예: ~/shared-claude-config/)에 두고, 쓰고 싶은 프로젝트에서만 심볼릭 링크를 걸어 연결합니다.

# ~/shared-claude-config/install.sh — 연결하고 싶은 저장소 루트에서 실행
SRC="$HOME/shared-claude-config"
mkdir -p .claude/agents .claude/skills
for agent in doc-researcher doc-fact-checker doc-writer; do
  ln -sf "$SRC/agents/$agent.md" ".claude/agents/$agent.md"
done
ln -sf "$SRC/skills/doc-refresh" ".claude/skills/doc-refresh"

이렇게 하면 실체는 ~/shared-claude-config 한 곳에서만 관리하면서, 필요한 저장소에만 골라서 연결할 수 있습니다. 심볼릭 링크는 절대경로라 다른 컴퓨터에서 이 저장소를 clone하면 깨지므로, 연결한 프로젝트의 .gitignore에 링크 경로를 추가해서 커밋되지 않게 해두는 걸 잊지 마세요.

07실제로 써보기

파일 4개(에이전트 3개 + 스킬 1개)를 두었다면, 다음 세션부터 바로 잡힙니다.

  1. 연결한 프로젝트를 새로 열거나 새 세션을 시작합니다. (이미 켜져 있던 세션은 시작할 때 스킬 목록을 이미 불러온 상태라 인식하지 못할 수 있습니다.)
  2. /doc-refresh <점검할 문서 경로> 처럼 스킬 이름을 직접 부르거나, "이 문서 최신 정보로 갱신해줘" 처럼 자연어로 요청합니다. 스킬의 description이 이런 요청과 맞아떨어지면 자동으로 호출됩니다.
  3. 진행되는 동안 리서처 → 팩트체커 → 라이터 순으로 결과가 쌓입니다. 중간에 UNCERTAIN이나 INCORRECT로 판정된 항목도 함께 보고되니 눈여겨보세요 — 이것도 값진 결과입니다.
  4. 마지막에 위치/기존/변경/근거가 정리된 초안을 받습니다. 여기서 검토하고 승인해야 실제 파일이 바뀝니다.
처음 써볼 때 좋은 대상

분량이 짧고, 사실 관계가 명확한 문서로 먼저 시도해보세요. 예: "이 프레임워크 버전이 최신인지 확인해줘" 같은 좁은 범위. 결과 품질을 눈으로 확인한 뒤 점점 범위를 넓히는 게 안전합니다.

08체크리스트

만들 때 지킬 것

  • 조사·검증 에이전트에는 Write/Edit을 주지 않는다tools 목록에서 아예 뺀다. "쓰지 말라고 프롬프트에 적기"보다 훨씬 확실하다.
  • 검증 단계는 리서처와 다른 질문을 던지게 시킨다"맞는지 다시 봐줘"가 아니라 "원출처에서 처음부터 다시 확인해줘".
  • 사람 승인 게이트를 스킬 절차에 명시한다승인 전에는 Edit을 부르지 않는다고 SKILL.md에 문장으로 못박는다.
  • 확신도/판정을 강제로 붙이게 한다"확인됨/추정/불확실"이 없으면 나중에 뭘 더 검증해야 할지 알 수 없다.

쓰지 말아야 할 때

  • 문서에 시간에 민감한 내용이 거의 없을 때개념 설명 위주 문서는 이 파이프라인을 돌릴 이유가 없다.
  • 사람 리뷰 없이 자동으로 계속 바뀌어야 할 때이 설계는 승인 게이트가 핵심이라 완전 자동화와는 맞지 않는다. 자동화하려면 게이트를 없애는 게 아니라, 승인 대상을 사람이 아닌 별도 검증 기준으로 바꿔야 한다.
